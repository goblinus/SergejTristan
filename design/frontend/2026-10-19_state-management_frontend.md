# Управление состоянием фронтенда (MVP)

Дата: 2026-10-19. Статус: проект, раунд 3 (доработка по ревью system-designer
раунда 2; решения Р-3, Р-4, Р-6, Р-7).

Закрываемый вопрос: **предсказуемое состояние без лишних зависимостей** —
границы серверного и локального состояния, Pinia vs композаблы, правила
инвалидации после постановки/снятия сторожка (включая undo).

## 1. Два вида состояния

| Вид | Источник истины | Примеры в MVP | Время жизни |
|-----|-----------------|---------------|-------------|
| **Серверное** | Бэкенд (БД) | справочник тикеров; собрания и отсечки за период; список сторожков | Кэшируется на время сессии, инвалидируется по мутациям и TTL |
| **Локальное** | Пользовательский ввод в текущем сеансе | выбранный месяц календаря; строка поиска тикера; свёрнутость «Прошедшие»; активный маршрут и `?meeting=<id>` | Живёт в компоненте/экране, глобально не сохраняется |

Главное правило: **серверное состояние не дублируется в локальное**.
Например, список отслеживаемых тикеров существует только в кэше
`useWatchlist()`, экран лишь проецирует его через computed.

Второе правило раунда 2: **статус сторожка клиентом не вычисляется**
(Р-3/Р-4): фронтенд потребляет готовые `status` (`no_date | far | near |
hot | critical | past`) и `days_to_event` из API и только отображает их.
Роли разделены (решение владельца от 2026-10-22): `status` → текст и иконка
чипа в `DeadlineIndicator` (C-07), `days_to_event` → цвет чипа через
`utils/deadline.ts:deadlineTone()` (`0` / `1..7` / `>7`, порог недели —
`DEADLINE_WEEK_DAYS = 7`). Клиент вычисляет только тон, но не статус.
Исключение — карточки календаря без сторожка: для них допустима локальная
оценка зоны по датам с порогами по умолчанию (T=7, граница 14, §4
«индикация-сроков» ui); цвет при этом берётся из той же шкалы по локально
посчитанным дням.

## 2. Решение: Pinia не нужна, достаточно композаблов

Обоснование:
- Четыре независимых серверных ресурса (tickers, meetings, record-dates,
  watchlist) — мало «перекрёстного» состояния, нечего централизовать.
- Нет потребности в devtools для состояния и time-travel — MVP.
- Разделяемый кэш легко реализуется `reactive` на уровне модуля
  композабла (singleton-экземпляр состояния).
- Минус одна зависимость и один рантайм-контракт.

Критерий пересмотра решения: появление ≥ 5 разделяемых серверных ресурсов,
глобального пользовательского состояния (авторизация) или потребности в
гидрации/SSR.

## 3. Композаблы и их состояние

### 3.1. `useCalendar()`

Модульное (разделяемое) состояние:

```ts
// состояние модуля — один кэш на всё приложение, ключ "from..to"
const cache = reactive({
  meetings: new Map<string, Page<Meeting>['items']>(),
  recordDates: new Map<string, Page<RecordDate>['items']>(),
  loadedAt: 0,
});
```

Загрузка периода — **два параллельных запроса** (замечание frontend-6, Р-6):
`getMeetings({ from, to })` и
`getRecordDates({ from, to, kind: 'dividend_payment' })`. Отсечки без
связанного собрания (`meeting_id IS NULL`) не приходят в `/meetings`,
поэтому без второго запроса они не попали бы в календарь и UpcomingList.

Публичный интерфейс — `AsyncState` + проекции (computed):

- `cards: ComputedRef<MeetingCardModel[]>` — карточки сетки S1 за выбранный
  месяц: по одной на собрание; модель объединяет `Meeting` (включая
  `logo_url`, `dividend` и `dsi`, ADR-0005/0006) и связанные поля сторожка
  (подсветка «отслеживается» — через `watchedTickers` из `useWatchlist`);
  `status` чипа — серверный, если тикер в сторожках, иначе локальная оценка
  зоны по датам (T=7); цвет чипа в обоих случаях — `deadlineTone()` по
  числу дней (0 / 1..7 / >7);
- `upcoming: ComputedRef<UpcomingItemModel[]>` — ближайшие отсечки
  `dividend_payment` за период, отсортированные по `record_date`;
  **включает отсечки без собрания** (`meeting_id === null` — берутся из
  `recordDates`, а не из meetings);
- `past/present`-разбиение — фильтр «Показать прошедшие» (секция
  «Прошедшие» сворачивается; прошедшие карточки рендерятся приглушёнными,
  зона `past`);
- `fetchedAtMin: ComputedRef<string | null>` — минимальный `fetched_at`
  среди показанных записей для индикатора «обновлено N назад» (Р-6;
  `null` → метка скрыта);
- `setMonth(month)`, `reload()`.

### 3.2. `useMeetingDialog()`

Состояние модала деталей (C-08), привязанное к query `?meeting=<id>`:

- `meetingId: ComputedRef<number | null>` — парсинг/валидация query;
- данные: ищет собрание в кэше `useCalendar`; промах кэша (deep-link после
  перезагрузки) → `getMeeting(id)` (GET `/meetings/{id}`, Р-6) с
  `isLoading/error` — состояния скелетона и «Собрание не найдено» (404);
- `open(id)` / `close()` — запись/удаление query-параметра через
  `router.replace`.

### 3.3. `useWatchlist()`

Модульное состояние:

```ts
const state = reactive({
  items: null as WatchlistItem[] | null,
  isLoading: false,
  error: null as ApiError | null,
});
```

Публичный интерфейс:
- `items / isLoading / error / reload` — как в `AsyncState`;
- список фильтруется `StatusFilterChips` (C-10) через computed:
  «все» / «горячие» (`hot`, `critical`) / «без даты» (`no_date`) /
  «прошла» (`past`); канонический серверный порядок (Р-7): сначала
  датированные сторожки по возрастанию `next_record_date` (эквивалентно
  зональному порядку `critical → hot → near → far`), затем `no_date`,
  затем `past`; перестановку зон клиент не делает;
- `isWatched(ticker)` — для подсветки в календаре и в автодополнении
  («Уже отслеживается», кнопка disabled);
- `add(ticker)` / `remove(ticker)` / `undoRemove()` — мутации (§4);
- `watchedTickers: ComputedRef<Set<string>>` — набор кодов тикеров для
  подсветки (реактивно, без перезагрузки календаря).

### 3.4. `useTickersSearch(query)`

- Локальное состояние вызывающего экрана (не модульное): `results,
  isLoading, error`.
- Debounce 300 мс внутри композабла; `AbortController` отменяет предыдущий
  поисковый запрос; минимум 2 символа (по C-04).
- Запрос к `GET /tickers?q=...&page_size=20`; результаты не кэшируются
  между экранами — поиск точечный, запрос дёшев.
- Состояния dropdown (empty/typing/loading/results/no-results/
  already-watched/error) — по вариантам C-04; `already-watched` — через
  `isWatched`.

### 3.5. `useSnackbar()`

Модульная очередь уведомлений для `SnackbarHost` (C-12):

```ts
interface Snack {
  id: number;
  kind: 'success' | 'error';
  text: string;
  action?: { label: string; run: () => void }; // «Отменить» / «Повторить»
}
```

- Автозакрытие через 5 сек (undo-окно), пауза по hover; показ по одному.
- `aria-live="polite"` на хосте (доступность, ui-гайд §7).

### 3.6. `useConnectivity()`

- `isOffline: Ref<boolean>` — события `window` `online`/`offline` +
  последняя `ApiError` c `kind: 'network'` (приложение может быть онлайн,
  а бэкенд — недоступен).
- Потребители: offline-бейдж в AppHeader, StateBanner offline, блокировка
  интерактивных действий.

## 4. Мутации сторожка и undo (замечание frontend-4)

Мутации: `useWatchlist().add() / .remove() / .undoRemove()`.
Семантика API идемпотентна (POST → 201 при создании, 200 при повторе),
этим пользуется undo.

Правила (единственный порядок, без optimistic-дублирования истины):

1. **add(ticker):** `POST /watchlist { ticker }` → по ответу обновить кэш
   (`created=true` (201) → Snackbar success «Сторожок установлен»;
   `false` (200) → «Уже отслеживается»). Пока идёт запрос — `isMutating`
   на кнопке (блокирует повторный клик).
2. **remove(ticker):** `DELETE /watchlist/{ticker}` выполняется сразу
   (не отложенная отправка) → элемент убирается из кэша по коду тикера
   (перед удалением снимок `{ ticker, threshold_days }` сохраняется) →
   Snackbar success «Сторожок снят» с action «Отменить» (окно 5 сек).
3. **undoRemove():** повторный `POST /watchlist { ticker, threshold_days }`
   из снимка → обновление кэша по ответу → Snackbar success «Восстановлено».
   Если окно истекло/страница перезагружена — undo недоступно (Snackbar
   уже закрыт; снимок живёт в памяти композабла, не persist).
4. **Ошибки мутаций:** состояние не меняем (данные на сервере не
   изменились — откат не нужен) → Snackbar error с action «Повторить»
   (повторно вызывает ту же мутацию). 404 на POST («ticker not found»)
   — Snackbar error без повтора.
5. **Инвалидация календаря не требуется:** подсветка «отслеживается» на S1
   строится из `watchedTickers` (computed) и зоны карточек пересчитываются
   реактивно (сторожок → серверный `status`); сеть не задействована.

TTL-кэш: `useCalendar` статичен внутри сессии; триггеры обновления —
кнопка «Обновить» (AppHeader → `reload()` активного ресурса), смена
месяца и переход на экран при `loadedAt` старше 1 часа (данные могли
обновиться сборщиком).

## 5. Локальное состояние экранов

Хранится в `ref` внутри page-компонента, наружу не выходит:

| Экран | Локальное состояние | Синхронизация |
|-------|--------------------|----------------|
| CalendarPage (`/calendar`) | выбранный месяц; чекбокс «Показать прошедшие»; свёрнутость секций | месяц — локально (шарибельность периода в MVP не требуется); модал — `?meeting=<id>` в URL (deep-link) |
| WatchlistPage (`/me`) | `searchQuery`; активный чип фильтра статусов | префилл поиска — одноразовый `?ticker=<CODE>` из URL (после применения удаляется) |

Состояние в URL — ровно то, что описано в
[2026-10-19_routing_frontend](./2026-10-19_routing_frontend.md);
остальное не переживает перезагрузку — приемлемо для MVP.

## 6. Что гарантированно не добавляем (MVP)

- Pinia / Vuex / TanStack Query — избыточны для четырёх ресурсов.
- localStorage/persist — нет требования восстанавливать состояние (undo-
  снимок сторожка — только в памяти на время undo-окна).
- Клиентский расчёт порогов статуса сторожка (Р-3) — сервер отдаёт готовые
  `status`/`days_to_event`; клиент вычисляет только визуальный тон
  (`deadlineTone()`, §1) по числу дней.
- WebSocket/SSE подписки на изменения календаря — опрос при переходах и
  кнопка «Обновить» достаточны.
- Пользовательская настройка `threshold_days` через интерфейс (Р-5) —
  поле есть в API, UI-редактирования в MVP нет (undo восстанавливает
  прежнее значение из снимка).

## 7. Открытые вопросы

Открытых вопросов нет: авторизация вне MVP подтверждена (Р-5), состав
состояния в URL зафиксирован картой экранов ui и роутингом (Р-6).
