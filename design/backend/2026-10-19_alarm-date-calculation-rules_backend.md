# 2026-10-19 — Правила расчёта статуса «сторожка» (backend)

## Назначение документа

Где и как вычисляется «приближение даты отсечки» для сторожков: место расчёта, выбор события (отсечка либо собрание), пороговые значения в сутках, поведение для дат в прошлом и сторожков без даты, шкала для согласования с ui.

**Решение владельца от 2026-10-22:** источником события сторожка является отсечка `dividend_payment`, а при её отсутствии — собрание акционеров с вопросом о дивидендах. Правило выбора события — раздел «Выбор события: отсечка → fallback на собрание»; оно заменяет прежнюю формулировку «сторожок смотрит только на `dividend_payment`». Решение принято владельцем проекта, не является предложением дизайнера и подлежит учёту при ревью system-designer.

## Место расчёта

Статус вычисляется **на чтении в API** — в сервисном слое при обработке `GET /api/v1/watchlist` (см. [2026-10-19_api-contract_backend](./2026-10-19_api-contract_backend.md)). В БД статус и число дней **не хранятся**: это производные от даты события (`record_dates.record_date` либо, в fallback-режиме, `shareholder_meetings.meeting_date`) и текущей даты; хранение создало бы задачу ежедневного пересчёта и риск рассинхронизации.

Расчёт на каждый запрос допустим для MVP: объём — один пользователь, десятки сторожков; две выборки по списку тикеров — ближайшие отсечки `dividend_payment` и ближайшие собрания с `dividend_question = true` (при наличии отсечки собрание нужно только для `next_meeting_date` и `next_dividend`).

Примечание о согласовании с system: ранний черновик контейнеров (`design/system/2026-10-19_containers-and-data-streaming_system.md`, поток 3) предполагал расчёт на клиенте. По задаче system-designer от 2026-10-19 расчёт перенесён в API (единое место правил, серверная дата, упрощение фронтенда). Настоящий документ — актуальная договорённость, подлежит подтверждению на ревью system-designer.

## Входные данные расчёта

Для сторожка (ticker, `threshold_days = T`):

1. Определяется **дата ближайшего будущего дивидендного события** `event_date` по правилу «отсечка → fallback на собрание» (раздел ниже). Отсечки `kind = 'meeting_participation'` событие сторожка не формируют ни в одном режиме.
2. `today` — текущая календарная дата сервера (наивная дата; сервер разворачивается локально у пользователя, московское время UTC+3, см. глоссарий system).
3. `D = (event_date - today).days` — целое число суток; `0` — событие сегодня. В ответе `event_date` передаётся как `next_record_date`, а `D` — как `days_to_event` (переименовано из `days_to_cutoff` решением владельца от 2026-10-22: поле означает дни до даты события, а не до отсечки).

## Выбор события: отсечка → fallback на собрание

Правило принято владельцем 2026-10-22. Причина: в реальных данных отсечка `dividend_payment` объявляется позже собрания и часто отсутствует вовсе, поэтому привязка сторожка только к отсечке оставляла компании, видимые в календаре собраний, без даты и метрик в строке S2.

Для тикера выбирается **одно** событие — ближайшее будущее; проверки выполняются по порядку, первое сработавшее правило определяет событие:

1. **Отсечка (приоритет).** Если есть записи `record_dates` с `kind = 'dividend_payment'` и `record_date >= today` — событие = минимальная такая отсечка. Тогда:
   - `next_record_date = record_date`;
   - `next_meeting_date` = дата собрания, связанного через `record_dates.meeting_id` (или `null`, если связь не установлена);
   - `next_dividend` = дивидендные условия этого собрания (или `null`).
2. **Собрание (fallback).** Иначе, если есть собрания `shareholder_meetings` с `dividend_question = true` и `meeting_date >= today` — событие = ближайшее такое собрание. Тогда:
   - `next_record_date = meeting_date` — дата события подставляется и в ячейку «Отсечка» строки S2; отдельной даты закрытия реестра в этом режиме не существует;
   - `next_meeting_date = meeting_date`;
   - `next_dividend` = дивидендные условия этого собрания (или `null`).
3. **Будущих событий нет** — см. таблицу статусов (`past` / `no_date`); `next_record_date`, `next_meeting_date`, `next_dividend`, `days_to_event` = `null`.

Отсечка имеет приоритет даже тогда, когда собрание наступает раньше: как только появляется `dividend_payment` на сегодня или позже, сторожок показывает отсечку, а не собрание. Это сохраняет прежнюю семантику ячейки «Отсечка» для основного сценария и обеспечивает переход на отсечку без изменения контракта.

Если у выбранной отсечки `meeting_id = null` (источник не связал дату с собранием), fallback на собрание **не применяется**: событием остаётся отсечка, `next_meeting_date` и `next_dividend` = `null`. Смешивать дату одной сущности с метриками другой нельзя.

## Шкала статусов

Каноническая шкала (решение system-designer Р-4, протокол ревью раунда 1): ровно шесть значений — `no_date`, `far`, `near`, `hot`, `critical`, `past`. Шкала едина с ui-зонами индикации сроков.

| Статус | Условие | Смысл |
|---|---|---|
| `critical` | `D = 0` | Событие сегодня (отсечка либо, в fallback-режиме, собрание). |
| `hot` | `1 <= D <= T` | Событие наступило по сроку сторожка (по умолчанию — неделя). |
| `near` | `T < D <= S` | Событие приближается. |
| `far` | `D > S` | До события далеко. |
| `past` | будущих событий нет, есть прошедшее | Прошедшее событие: отсечка `dividend_payment` с `record_date < today` либо собрание с `dividend_question = true` и `meeting_date < today`. Новых данных нет. |
| `no_date` | событий нет вообще | У тикера нет ни отсечек `dividend_payment`, ни собраний с вопросом о дивидендах (в том числе прошедших). |

Пороги:

- `T = threshold_days` сторожка (хранится в `watchlist_items`, по умолчанию 7; задаётся при создании, допустимый диапазон 1..365). Граница зоны `hot`.
- `S = DIVCAL_WATCH_SOON_DAYS` — константа конфигурации, по умолчанию **14 суток**. Граница зоны `near`, общая для всех сторожков.

Инвариант конфигурации: `T < S`; при нарушении (пользователь задал `threshold_days >= 14`) граница `near` фактически схлопывается: интервалы проверяются в порядке `critical → hot → near → far`, поэтому `critical`/`hot` получают приоритет, поведение остаётся корректным.

## Граничные случаи

- **Событие сегодня** (`D = 0`): статус `critical` — отдельное значение шкалы, не входит в `hot` (интервал `hot` — `1..T` включительно). Относится и к отсечке, и к собранию в fallback-режиме.
- **Дата в прошлом**: не участвует в выборе «ближайшего будущего». Если будущих событий нет, а прошедшие есть — `past`; поля `next_record_date`, `next_meeting_date`, `next_dividend`, `days_to_event` в ответе — `null`. Прошедшие события в ответ сторожка не включаются (фронтенд может получить отсечки через `/record-dates?to=<today>`, собрания — через `/meetings?from&to`).
- **Прошедшая отсечка и будущее собрание**: статус не `past` — срабатывает fallback, событием становится собрание, `D` считается от `meeting_date`. `past` возможен только при отсутствии любого будущего события.
- **Будущая отсечка и более раннее будущее собрание**: событием остаётся отсечка (приоритет отсечки), даже если дата собрания ближе к `today`; `D` считается от `record_date`.
- **Собрание в прошлом при будущей отсечке**: штатная ситуация — реестр закрывается после собрания. `next_meeting_date` может быть раньше `today`, это не влияет на статус: `D` считается от `record_date` и остаётся `>= 0`.
- **Отсечка без связи с собранием** (`meeting_id = null`): `next_meeting_date = null`, `next_dividend = null`; fallback на собрание не применяется.
- **Собрание без вопроса о дивидендах** (`dividend_question = false`): в выборе события не участвует ни как будущее, ни как прошедшее.
- **Отсечка `meeting_participation`**: в выборе события не участвует ни в одном режиме (в том числе при отсутствии `dividend_payment`).
- **Сторожок без событий** (`no_date`): `next_record_date = null`, `next_meeting_date = null`, `next_dividend = null`, `days_to_event = null`, статус `no_date`. Требует отдельного визуального состояния; положение в списке — см. раздел «Сортировка списка сторожков».
- **Несколько будущих отсечек тикера**: берётся минимальная. Несколько будущих собраний — аналогично минимальное.
- **Снятый с торгов тикер** (`is_active = false`) со сторожком: расчёт не меняется; отображение признака неактивности — зона фронтенда (поле `is_active` в ответ можно добавить при необходимости — задел, не обязательство MVP).

## Пример

`today = 2026-10-19`, `T = 7`, `S = 14`. `event_date` — дата, выбранная по правилу «отсечка → fallback на собрание»; в ответе она передаётся как `next_record_date`.

| event_date | источник события | D | status |
|---|---|---|---|
| 2026-10-19 | отсечка `dividend_payment` | 0 | critical |
| 2026-10-25 | отсечка `dividend_payment` | 6 | hot |
| 2026-10-26 | собрание (fallback) | 7 | hot |
| 2026-10-27 | отсечка `dividend_payment` | 8 | near |
| 2026-11-02 | собрание (fallback) | 14 | near |
| 2026-11-03 | отсечка `dividend_payment` | 15 | far |
| (только 2026-06-14) | прошедшее событие | — | past |
| (событий нет) | — | — | no_date |

**Пример fallback.** У тикера прошла отсечка `dividend_payment` 2026-06-14, есть собрание с `dividend_question = true` на 2026-11-02, отсечка для него не объявлена. Результат: `next_record_date = 2026-11-02`, `next_meeting_date = 2026-11-02`, `next_dividend` — условия этого собрания, `days_to_event = 14`, `status = near`. Без fallback сторожок получил бы `past` и пустые поля, хотя будущее событие известно.

## Сортировка списка сторожков

Порядок элементов `GET /api/v1/watchlist` — канонический, закреплён решением Р-7 ревью раунда 2 совместно с ui (список S2, §7 `design/ui/2026-10-19_dates-indicators_ui.md`):

1. **датированные** сторожки (есть `next_record_date`, в том числе полученный по fallback от собрания) — по `next_record_date` ASC. Поскольку статус монотонно зависит от `D`, это эквивалентно зональному порядку `critical -> hot -> near -> far`; внутри одной зоны — более ранняя дата выше;
2. **статус `no_date`** — `next_record_date IS NULL`, событий нет вообще (ни отсечек `dividend_payment`, ни собраний с вопросом о дивидендах); между собой по `ticker` ASC;
3. **статус `past`** — `next_record_date IS NULL`, есть прошедшее событие (отсечка `dividend_payment` с `record_date < today` либо собрание с `dividend_question = true` и `meeting_date < today`); между собой по `ticker` ASC.

То есть NULL-блок не един: `no_date` всегда выше `past`, смешивание недопустимо. Реализация — сортировка по составному ключу (`status_rank`, `next_record_date NULLS LAST`, `ticker`), где `status_rank`: `no_date -> 1`, `past -> 2`, датированные -> `0`; либо предварительный расчёт статуса в сервисном слое с сортировкой по тому же ключу (для MVP с десятками сторожков целесообразен второй вариант — статус и так вычисляется на чтении).

## Согласование со шкалой ui

Фронтенд/ ui-дизайнер определяет только **отображение** (цвет, метка) для шести состояний канонической шкалы: `no_date`, `far`, `near`, `hot`, `critical`, `past`. Контракт закреплён (решение Р-4):

- множество значений `status` — ровно эти шесть строк, регистр нижний, локализация — на фронтенде;
- граница `hot` индивидуальна для сторожка (`threshold_days`), граница `near` фиксирована конфигурацией (`DIVCAL_WATCH_SOON_DAYS`, по умолчанию 14);
- `days_to_event` передаётся вместе со статусом, поэтому интерфейс может показывать и число дней, и состояние без собственного пересчёта.

Изменение множества статусов или порогов — изменение API-контракта, требует нового согласования (system-designer).
