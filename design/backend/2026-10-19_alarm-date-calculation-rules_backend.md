# 2026-10-19 — Правила расчёта статуса «сторожка» (backend)

## Назначение документа

Где и как вычисляется «приближение даты отсечки» для сторожков: место расчёта, пороговые значения в сутках, поведение для дат в прошлом и сторожков без даты, шкала для согласования с ui.

## Место расчёта

Статус вычисляется **на чтении в API** — в сервисном слое при обработке `GET /api/v1/watchlist` (см. [API-контракт](./2026-10-19_api-контракт_backend.md)). В БД статус и число дней **не хранятся**: это производные от `record_dates.record_date` и текущей даты; хранение создало бы задачу ежедневного пересчёта и риск рассинхронизации.

Расчёт на каждый запрос допустим для MVP: объём — один пользователь, десятки сторожков; один запрос выборки ближайших отсечек по списку тикеров.

Примечание о согласовании с system: ранний черновик контейнеров (`design/system/2026-10-19_контейнеры-и-потоки_system.md`, поток 3) предполагал расчёт на клиенте. По задаче system-designer от 2026-10-19 расчёт перенесён в API (единое место правил, серверная дата, упрощение фронтенда). Настоящий документ — актуальная договорённость, подлежит подтверждению на ревью system-designer.

## Входные данные расчёта

Для сторожка (ticker, `threshold_days = T`):

1. Берётся **ближайшая будущая** дата отсечки тикера: минимальный `record_date >= today` среди записей `kind = 'dividend_payment'` (отсечки для участия в собрании статус не формируют).
2. `today` — текущая календарная дата сервера (наивная дата; сервер разворачивается локально у пользователя, московское время UTC+3, см. глоссарий system).
3. `D = (next_record_date - today).days` — целое число суток; `0` — отсечка сегодня.

## Шкала статусов

Каноническая шкала (решение system-designer Р-4, протокол ревью раунда 1): ровно шесть значений — `no_date`, `far`, `near`, `hot`, `critical`, `past`. Шкала едина с ui-зонами индикации сроков.

| Статус | Условие | Смысл |
|---|---|---|
| `critical` | `D = 0` | Отсечка сегодня. |
| `hot` | `1 <= D <= T` | Отсечка наступила по сроку сторожка (по умолчанию — неделя). |
| `near` | `T < D <= S` | Отсечка приближается. |
| `far` | `D > S` | До отсечки далеко. |
| `past` | будущих дат нет, есть прошедшие | Последняя известная отсечка уже прошла; новых данных нет. |
| `no_date` | у тикера нет ни одной записи `dividend_payment` | Дата отсечки неизвестна (собрание может быть объявлено без отсечки). |

Пороги:

- `T = threshold_days` сторожка (хранится в `watchlist_items`, по умолчанию 7; задаётся при создании, допустимый диапазон 1..365). Граница зоны `hot`.
- `S = DIVCAL_WATCH_SOON_DAYS` — константа конфигурации, по умолчанию **14 суток**. Граница зоны `near`, общая для всех сторожков.

Инвариант конфигурации: `T < S`; при нарушении (пользователь задал `threshold_days >= 14`) граница `near` фактически схлопывается: интервалы проверяются в порядке `critical → hot → near → far`, поэтому `critical`/`hot` получают приоритет, поведение остаётся корректным.

## Граничные случаи

- **Отсечка сегодня** (`D = 0`): статус `critical` — отдельное значение шкалы, не входит в `hot` (интервал `hot` — `1..T` включительно).
- **Дата в прошлом**: не участвует в выборе «ближайшей будущей». Если будущих нет, а прошедшие есть — `past`; поле `next_record_date`/`days_to_cutoff` в ответе — `null`. Прошедшие даты в ответ сторожка не включаются (фронтенд может получить их через `/record-dates?to=<today>`).
- **Сторожок без даты** (`no_date`): `next_record_date = null`, `days_to_cutoff = null`, статус `no_date`. Требует отдельного визуального состояния; положение в списке — см. раздел «Сортировка списка сторожков».
- **Несколько будущих отсечек тикера**: берётся минимальная.
- **Снятый с торгов тикер** (`is_active = false`) со сторожком: расчёт не меняется; отображение признака неактивности — зона фронтенда (поле `is_active` в ответ можно добавить при необходимости — задел, не обязательство MVP).

## Пример

`today = 2026-10-19`, `T = 7`, `S = 14`:

| next_record_date | D | status |
|---|---|---|
| 2026-10-19 | 0 | critical |
| 2026-10-25 | 6 | hot |
| 2026-10-26 | 7 | hot |
| 2026-10-27 | 8 | near |
| 2026-11-02 | 14 | near |
| 2026-11-03 | 15 | far |
| (только 2026-06-14) | — | past |
| (нет записей) | — | no_date |

## Сортировка списка сторожков

Порядок элементов `GET /api/v1/watchlist` — канонический, закреплён решением Р-7 ревью раунда 2 совместно с ui (список S2, §7 `design/ui/2026-10-19_индикация-сроков_ui.md`):

1. **датированные** сторожки (есть `next_record_date`) — по `next_record_date` ASC. Поскольку статус монотонно зависит от `D`, это эквивалентно зональному порядку `critical -> hot -> near -> far`; внутри одной зоны — более ранняя дата выше;
2. **статус `no_date`** — `next_record_date IS NULL` без прошедших записей `dividend_payment`; между собой по `ticker` ASC;
3. **статус `past`** — `next_record_date IS NULL`, прошедшие записи есть; между собой по `ticker` ASC.

То есть NULL-блок не един: `no_date` всегда выше `past`, смешивание недопустимо. Реализация — сортировка по составному ключу (`status_rank`, `next_record_date NULLS LAST`, `ticker`), где `status_rank`: `no_date -> 1`, `past -> 2`, датированные -> `0`; либо предварительный расчёт статуса в сервисном слое с сортировкой по тому же ключу (для MVP с десятками сторожков целесообразен второй вариант — статус и так вычисляется на чтении).

## Согласование со шкалой ui

Фронтенд/ ui-дизайнер определяет только **отображение** (цвет, метка) для шести состояний канонической шкалы: `no_date`, `far`, `near`, `hot`, `critical`, `past`. Контракт закреплён (решение Р-4):

- множество значений `status` — ровно эти шесть строк, регистр нижний, локализация — на фронтенде;
- граница `hot` индивидуальна для сторожка (`threshold_days`), граница `near` фиксирована конфигурацией (`DIVCAL_WATCH_SOON_DAYS`, по умолчанию 14);
- `days_to_cutoff` передаётся вместе со статусом, поэтому интерфейс может показывать и число дней, и состояние без собственного пересчёта.

Изменение множества статусов или порогов — изменение API-контракта, требует нового согласования (system-designer).
