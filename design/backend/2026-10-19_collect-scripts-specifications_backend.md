# 2026-10-19 — Спецификация скриптов сбора данных (backend)

## Назначение документа

Единый формат и контракт офлайн-скриптов сбора сущфактов из официальных источников (moex.com ISS API, disclosure.ru / e-disclosure), нормализация в каноническую модель, идемпотентный upsert, логирование, CLI-интерфейс, поведение при недоступности источника.

Основание: контейнер «Data collectors» и поток 1 в [2026-10-19_containers-and-data-streaming_system](../system/2026-10-19_containers-and-data-streaming_system.md), ADR-0003 (стратегия обновления данных — upsert), [2026-10-19_database-schema_backend](./2026-10-19_database-schema_backend.md).

См. диаграмму пайплайна: [2026-10-19_collect-pipeline_backend](./2026-10-19_collect-pipeline_backend.puml).

## Роль в системе

Скрипты — **единственный писатель доменных данных** (`tickers`, `shareholder_meetings`, `record_dates`). Backend API доменные данные только читает. Запуск — вручную или по расписанию ОС (cron / Task Scheduler); внутри API фоновых задач нет.

## Пайплайн (единый для всех скриптов)

Каждый скрипт реализует четыре стадии:

1. **fetch (источник → сырой ответ)** — HTTP-запросы к источнику (`scripts/ingestion/sources/*.py`). Синхронный `httpx.Client`; таймаут `DIVCAL_HTTP_TIMEOUT_SECONDS` (30 c), повторные попытки `DIVCAL_HTTP_RETRIES` (3) с экспоненциальной задержкой (1 c, 2 c, 4 c) для сетевых ошибок и HTTP 5xx/429. HTTP 4xx не ретраится.
2. **parse (сырой ответ → разобранные факты)** — структурный разбор JSON (MOEX ISS) / HTML (disclosure) в промежуточные словари (`scripts/ingestion/parsers/*.py`). Парсер не ходит в сеть и не пишет в БД — тестируется на зафиксированных файлами ответах из `tests/fixtures/`.
3. **normalize (факты → канонические DTO)** — приведение к канонической модели system (`scripts/ingestion/normalize.py`): регистр тикера, типы собраний, валидация дат, отбраковка неполноценных записей, разбор периода и суммы дивиденда. Результат — Pydantic-DTO нормализации (`NormalizedTicker`, `NormalizedMeeting`, `NormalizedRecordDate`, `NormalizedDividendMetrics`) — отдельные от API-схем.
4. **load (DTO → БД)** — идемпотентный upsert (`scripts/ingestion/loader.py` → `app/repositories/`). По бизнес-ключу: `tickers.ticker`; `shareholder_meetings (ticker_id, meeting_date, meeting_type)`; `record_dates (ticker_id, record_date, kind)`. Существующая запись обновляется (поля данных + `source_url`, `fetched_at`); новая — вставляется. Повторный запуск по тем же данным не создаёт дублей и меняет только `fetched_at`.

Стадии слабо связаны: границы между ними — чистые функции над DTO, что позволяет тестировать parse/normalize без сети и БД, а load — без источника.

Исключение — `sync_logos.py`: у него нет сетевого источника, стадии fetch/parse/normalize вырождены в «прочитать каталог репозитория и провалидировать файлы» (см. раздел скрипта ниже).

Сырые ответы источников на диске (кэш/аудит) — вне MVP-гарантий (см. поток 1 system).

## Набор скриптов MVP

### fetch_tickers_moex.py — список тикеров MOEX

- **Источник**: MOEX ISS API, JSON: `https://iss.moex.com/iss/engines/stock/markets/shares/securities.json` (доска по умолчанию — основной режим `TQBR`; параметры: `iss.meta=off`, постраничный обход `start=`).
- **Результат**: upsert в `tickers` (`ticker` ← SECID, `short_name` ← SHORTNAME, `isin` ← ISIN, `board`, `lot_size` ← LOTSIZE; `last_price` и `price_updated_at` — из блока marketdata того же ответа MOEX ISS, последняя сделка/цена закрытия).
- **Обработка исчезнувших тикеров**: в конце успешного прогона тикеры, собранные ранее из этого источника, но отсутствующие в текущем ответе и не появлявшиеся ранее на этой доске, помечаются `is_active = FALSE` (не удаляются — у них могут быть собрания/сторожки). При неуспешном прогоне деактивации **не производится** (защита от массовой пометки при сбое источника).
- **Расписание**: 1 раз в сутки (ночной запуск).

### sync_logos.py — логотипы эмитентов

Единственный скрипт набора без сетевого источника: набор ассетов лежит в репозитории, стадии fetch/parse/normalize вырождены (чтение каталога, валидация XML, построение соответствия «тикер → путь к логотипу»).

- **Источник**: курируемый набор SVG в `backend/assets/logos/{TICKER}.svg` (путь относительно каталога `backend/`). Не скрапинг и не хотлинк сайтов эмитентов (ADR-0006); набор пополняется, заменяется и удаляется вручную в репозитории.
- **Сопоставление с тикером**: имя файла без расширения сравнивается с `tickers.ticker` без учёта регистра (`sber.svg`, `Sber.svg` → `SBER`); в БД, в имени файла статики и в `logo_url` тикер всегда в верхнем регистре.
- **Коллизия имён**: если регистронезависимо на один тикер претендуют несколько файлов (`sber.svg` и `SBER.svg`), файлы обходятся в алфавитном порядке имён, берётся первый, остальные логируются WARNING и игнорируются.
- **Валидация ассета**: файл должен разбираться как XML и иметь корневой элемент `svg` (namespace `http://www.w3.org/2000/svg` допускается). Файл, который не является корректным XML или не является SVG, логируется WARNING и пропускается — соответствующий тикер обрабатывается как «ассета нет»; прогон продолжается.
- **Результат**: валидные файлы копируются в статику API `backend/static/logos/{TICKER}.svg` (отдаётся по `/static/logos/{TICKER}.svg`; каталог монтируется как `StaticFiles` в `app/main.py`), в `tickers.logo_url` проставляется относительный путь `/static/logos/{TICKER}.svg`. Тикерам без ассета (файл отсутствует или не прошёл валидацию) проставляется `NULL` — UI покажет монограмму.
- **Объём обновления**: все записи `tickers`, включая `is_active = FALSE` — логотип является атрибутом эмитента, а не активного листинга (бумага может вернуться в листинг, а история по ней сохраняется). Новые тикеры скрипт не создаёт: синхронизируются только уже существующие строки, поэтому запуск — после `fetch_tickers_moex.py`. Скрипт меняет только поле `logo_url`: `source_url`/`fetched_at` и прочие поля тикера не затрагиваются (курируемый ассет не является сущфактом источника). Пустая таблица `tickers` — не ошибка конфигурации: валидные ассеты всё равно копируются в статику, число обновлённых строк — 0, прогон завершается кодом 0 (в лог — INFO о пустом справочнике и напоминание о запуске `fetch_tickers_moex.py`).
- **Идемпотентность**: файл в `static/logos/` перезаписывается только при отличии содержимого; `logo_url` обновляется только для строк, где текущее значение отличается от целевого (включая сброс в `NULL`). Повторный запуск при неизменном наборе не меняет ни файлов, ни строк БД. Устаревшие файлы в `static/logos/` не удаляются: они не адресуются из БД и не влияют на API; чистка каталога — ручная операция.
- **Защита от сбоя набора**: отсутствие каталога `assets/logos/` или отсутствие в нём хотя бы одного файла `*.svg` — ERROR и фатальный сбой: БД и `static/logos/` не изменяются, код возврата 1. Это защита от массового обнуления `logo_url`, если набор не смонтирован/неполон.
- **Ошибки уровня файла и уровня прогона**: ошибка чтения или валидации отдельного файла — WARNING, файл пропускается, остальные тикеры обрабатываются (код возврата 0); ошибка записи в статику или сбой БД — ERROR, код возврата 1. Код 2 как код частичного сбоя сбора этим скриптом не используется: источник локальный и единственный, частичный сбой одного файла не является сбоем источника.
- **`--dry-run`**: полный проход (чтение каталога, валидация, расчёт целевых значений `logo_url`) без копирования файлов и без записи в БД; в лог выводятся количество валидных и отброшенных ассетов и количество строк `tickers`, которые были бы изменены.
- **Коды возврата**: 0 — синхронизация выполнена (в том числе при WARNING по отдельным файлам); 1 — фатальная ошибка (нет каталога источника, нет ни одного `.svg`, ошибка записи в статику, недоступность БД) — см. общую таблицу кодов ниже.
- **CLI**: `uv run python -m scripts.sync_logos [--source assets] [--dry-run] [--verbose]`. Аргумент `--source` принимается для единообразия CLI с остальными скриптами: единственное допустимое значение — `assets` (значение по умолчанию); другое значение — ошибка разбора аргументов (argparse завершает с кодом 2), прогон не выполняется.
- **Расписание**: вручную при обновлении набора; в ежедневный цикл не входит.

### fetch_meetings_disclosure.py — собрания и даты отсечки

- **Источники** (в порядке приоритета, резерв при недоступности основного):
  1. disclosure.ru (Interfax ЦРКИ) — лента сообщений «о проведении собрания акционеров» / «о дате закрытия реестра» по эмитенту; разбор HTML.
  2. e-disclosure.ru — резервный источник тех же сущфактов.
- **Результат**: upsert в `shareholder_meetings` (только собрания с вопросом о дивидендах: детект по ключевым словам повестки — «дивиденд»; правило парсера) и в `record_dates` (обе разновидности `kind`; связь `meeting_id` проставляется, если дата отсечки и собрание совпадают по эмитенту и периоду — эвристика связывания в нормализаторе, иначе `NULL`). Дополнительно из формулировки решения извлекаются `dividend_period` (`year`/`half_year`/`quarter`) и `dividend_per_share` (₽ на акцию); если признак периода или сумма не распознаны — соответствующее поле `NULL`, запись всё равно сохраняется.
- **Объём обхода**: только тикеры из `tickers` с `is_active = TRUE` (активный листинг — источник перечня эмитентов).
- **Расписание**: 1 раз в сутки; при желании чаще в «дивидендный сезон» — без изменений кода, параметром расписания ОС.

### fetch_dividend_history_moex.py — DSI по истории дивидендов

- **Источник**: MOEX ISS, JSON `https://iss.moex.com/iss/securities/{secid}/dividends.json` — история дивидендов по тикеру (дата отсечки, сумма на акцию).
- **Объём**: только `tickers` с `is_active = TRUE`; горизонт — последние 5 завершённых календарных лет.
- **Расчёт**: годовые суммы DPS, затем DSI 0–100 по формуле из [2026-10-20_dividend-metrics_backend](./2026-10-20_dividend-metrics_backend.md). Меньше 3 лет с выплатами → `dsi = NULL` (не «0», чтобы не смешивать «нет истории» и «нестабильные выплаты»).
- **Результат**: upsert в `tickers` только полей `dsi`, `dsi_updated_at`; сами исторические выплаты в БД MVP не сохраняются.
- **Сбой источника**: прежнее значение `dsi` сохраняется, скрипт завершается кодом 2 (частичный сбой), лог ERROR по тикеру.
- **Расписание**: 1 раз в сутки, после `fetch_tickers_moex.py` (нужен актуальный список активных тикеров).

Новый источник добавляется как адаптер в `sources/` + парсер в `parsers/` без изменения normalize/loader и CLI-обвязки.

## CLI-интерфейс (единый контракт)

Все скрипты — консольные программы со стандартным интерфейсом (argparse):

```text
uv run python -m scripts.<имя> [--source <имя>] [--dry-run] [--verbose]
```

| Аргумент | Назначение |
|---|---|
| `--source` | Только для мультиисточниковых скриптов: ограничить сбор одним источником (например, `--source e-disclosure`). |
| `--dry-run` | Полный пайплайн без записи в БД: количество распознанных/готовых к upsert записей выводится в лог (проверка парсеров после смены вёрстки источника). |
| `--verbose` | Уровень логирования DEBUG вместо INFO. |

Коды возврата (для планировщика ОС и ручного контроля):

| Код | Значение |
|---|---|
| 0 | Сбор завершён успешно (все целевые источники отработали или резервный закрыл основной). |
| 1 | Фатальный сбой: пайплайн прерван (недоступна БД, ошибка конфигурации). |
| 2 | Частичный сбой: данные частично собраны, но хотя бы один источник/страница отказал (записи в БД сохранены, старые данные не испорчены). |

## Логирование

- stdlib `logging`, настройка из `app/core/logging.py`; уровень — `DIVCAL_LOG_LEVEL` (INFO по умолчанию), `--verbose` переопределяет в DEBUG.
- Формат строки: `2026-10-19T22:05:11Z INFO [fetch_meetings_disclosure] ticker=SBER stage=load upserted=3 skipped=1`.
- Обязательные точки лога: начало/конец скрипта с итоговой статистикой (получено/распознано/вставлено/обновлено/отброшено); каждая ошибка парсинга записи (WARNING, запись отбрасывается, прогон продолжается); каждый отказ источника (ERROR).
- Лог — stdout (перенаправление в файл — средствами ОС/планировщика).

## Недоступность и изменение источника

Принцип: **сбой источника не портит существующие данные и не блокирует фронтенд** (UI показывает последние успешно загруженные данные, см. допущения system).

- Источник недоступен/вернул 5xx после ретраев → для мультиисточникового скрипта переключение на резервный источник; для одиночного — завершение с кодом 1 (тикеры) после лога ERROR. Деактивация тикеров (см. выше) при этом не выполняется.
- Изменение формата ответа (неожиданная структура JSON/HTML) → парсер бросает доменное исключение на уровне записи/страницы, скрипт логирует ERROR и завершается кодом 2 (сохранившиеся части данных записаны). Полное молчаливое проглатывание запрещено: смена формата должна быть заметна по логу и коду возврата.
- Отдельная «битая» запись среди корректных → WARNING, запись отброшена, остальной прогон продолжается.
- Отсутствие данных по валидному запросу (пустой список собраний эмитента) — не ошибка: INFO-лог, upsert не выполняется.

## Идемпотентность и трассировка

- Upsert всегда по бизнес-ключу (см. схему БД). Дублирующие записи из источника дедуплицируются на стадии normalize.
- Каждая запись несёт `source_url` (канонический URL сущфакта у источника) и `fetched_at` (UTC-момент загрузки).
- Повторный запуск скрипта безопасен в любой момент; параллельный запуск двух копий одного скрипта в MVP не поддерживается (планировщик запускает экземпляры последовательно).

## Тестируемость

- Парсеры — модульные тесты на сохранённых ответах (`tests/fixtures/`: эталонные JSON/HTML).
- Нормализатор — тесты на DTO-входах, включая разбор периода/суммы дивиденда и `NULL` при нераспознанном значении.
- Расчёт DSI — unit-тесты формулы на синтетических рядах (полные/частичные годы, снижение выплат, менее 3 лет истории).
- Loader — тесты идемпотентности upsert на временной БД (повторный прогон не меняет состав записей).
- `sync_logos.py` — тесты на временных каталогах (источник и статика): регистронезависимое сопоставление имени файла с тикером, отбраковка битого/не-SVG файла, обновление неактивных тикеров, идемпотентность (повторный прогон не меняет файлы и строки), фатальный сбой при отсутствующем/пустом каталоге источника, `--dry-run` без записи.

## Что осознанно не проектируется (вне MVP)

- Очередь задач, Celery/RQ, Redis.
- Инкрементальный сбор «по дате изменения» у источника, rate-limit-бюджеты.
- Исторический бэкфилл глубже ближайших событий.
- Уведомления о сбоях сбора (контроль — через код возврата и лог).
