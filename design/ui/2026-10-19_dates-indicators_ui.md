# Индикация сроков дивидендной отсечки

Дата: 2026-10-19
Область: ui

Единые правила визуализации «приближения даты отсечки» для всех экранов (карточка собрания S1, строка сторожка S2, модал деталей S1.1). Источник токенов цвета — `2026-10-19_visual-style_ui.md`, реализация — компонент C-07 `DeadlineIndicator` из `2026-10-19_ui-component-kit_ui.md`.

## 1. Источник статуса (контракт с backend)

Статус сторожка **вычисляется на сервере** (решение Р-3): фронтенд получает в ответе `GET /api/v1/watchlist` поля `status` и `days_to_event` и **не реализует собственную логику порогов**. Каноническая шкала (решение Р-4) — ровно шесть идентификаторов, нижний регистр, без префиксов:

```
{ no_date, far, near, hot, critical, past }
```

Серверные правила (для понимания семантики; реализация — в `design/backend/2026-10-19_alarm-date-calculation-rules_backend.md`):

| Статус | Условие на сервере | Пороги |
|---|---|---|
| `critical` | событие сегодня (D = 0) | — |
| `hot` | 1 ≤ D ≤ T | T = `threshold_days` сторожка (персонально, по умолчанию 7, диапазон 1..365) |
| `near` | T < D ≤ 14 | граница 14 фиксирована конфигурацией (`DIVCAL_WATCH_SOON_DAYS`) |
| `far` | D > 14 | — |
| `past` | будущих событий нет, есть прошедшие (отсечка `dividend_payment` либо собрание с вопросом о дивидендах) | — |
| `no_date` | нет ни отсечки `dividend_payment`, ни собрания с вопросом о дивидендах (в том числе прошедших) | — |

Порядок проверки интервалов: `critical → hot → near → far`, что гарантирует корректность и при `T ≥ 14`.

`D = days_to_event` — число суток от текущей даты до даты выбранного события. Событием сторожка служит ближайшая будущая отсечка `dividend_payment`; если её нет — ближайшее будущее собрание с вопросом о дивидендах (fallback, решение владельца от 2026-10-22). В fallback-режиме дата собрания подставляется в `next_record_date`, поэтому ячейка «Отсечка» и индикатор срока относятся к дате собрания.

## 2. Семантика зон для пользователя

| Зона | Семантика |
|---|---|
| `no_date` | нет ни отсечки, ни собрания с вопросом о дивидендах — ожидание информации |
| `far` | далёкий горизонт, наблюдение |
| `near` | пора планировать |
| `hot` | приближение в пределах порога сторожка — основной акцент; жёлтый только при `days_to_event ≤ 7` |
| `critical` | сегодня — последний день до закрытия реестра (в fallback-режиме — день собрания) |
| `past` | событие завершено, будущих событий нет |

## 3. Визуальное кодирование: цвет — по числу дней, иконка и текст — по зоне

Решение владельца от 2026-10-22: цвет чипа C-07 определяется **числом дней до события** (`days_to_event`), а не зоной статуса. Порог недели фиксирован — **7 суток** — и не зависит от персонального `threshold_days` сторожка. Иконка, текст и доступность остаются привязанными к зоне `status`; зона цвет больше не задаёт.

### 3.1. Цвет по числу дней

Правило применяется по первому совпадению сверху вниз (приоритет — в первом столбце):

| Приоритет | Условие | Цвет текста/иконки | Подложка чипа | Граница |
|---|---|---|---|---|
| 1 | `status = past` либо `days_to_event < 0` | `--on-surface-muted` | `--surface-1` | 1px `--outline-variant` |
| 2 | `days_to_event = 0` | `--danger` | `--danger-container` | — |
| 3 | `1 ≤ days_to_event ≤ 7` | `--warn` | `--warn-container` | — |
| 4 | `days_to_event > 7` | `--success` | `--success-container` | — |
| 5 | `days_to_event = null` и `status ≠ past` (то есть `no_date`) | `--on-surface-variant` | `--neutral-chip` | — |

Строка 1 идёт первой, потому что в статусе `past` сервер отдаёт `days_to_event = null` — то же значение, что и в `no_date`. Различие между ними делается по `status`, а не по числу дней.

### 3.2. Иконка и текст по зоне

| Зона | Иконка (Material Symbols Rounded) | Текст-подпись | Цвет (по §3.1) |
|---|---|---|---|
| `no_date` | `event_busy` | «нет даты» | нейтральный (`--neutral-chip` / `--on-surface-variant`) |
| `far` | `schedule` | «N дн.» | зелёный (`--success-container` / `--success`) |
| `near` | `event_upcoming` | «N дн.» | зелёный при N > 7; жёлтый при N ≤ 7 (возможно только при `T < N ≤ 7`) |
| `hot` | `warning` | «N дн.», «осталось N дн.» | жёлтый при N ≤ 7; зелёный при N > 7 |
| `critical` | `priority_high` | «сегодня!» | красный (`--danger-container` / `--danger`) |
| `past` | `event_available` | «прошла» | приглушённый (`--surface-1` / `--on-surface-muted` + `--outline-variant`) |

Примечания:
- `far` и `near` **оба зелёные**: граница 14 суток остаётся в шкале статусов, но на цвет не влияет — горизонт «больше недели» визуально однороден, зоны различаются только иконкой и текстом.
- `hot` жёлтый **только при `days_to_event ≤ 7`**. Если `status = hot`, но `days_to_event > 7` (персональный `threshold_days` больше 7; диапазон 1..365), цвет зелёный — порог недели не масштабируется персональной настройкой.
- Обратное следствие: при `threshold_days < 7` зона `near` может содержать дни 1..7, и такой чип будет жёлтым. Цвет определяется только числом дней, поэтому жёлтый не эквивалентен статусу `hot`.
- `critical` — красный. Красный (`--danger`) резервируется за «сегодня» и ошибками, чтобы не смешивать семантику. Зелёный (`--success`) означает «больше недели до события», а не «всё хорошо» и не «выплачено».
- Прошедшие события визуально приглушаются: строка/карточка на opacity 60%, чип — приглушённый. Красный для «прошла» не используем: «прошла» — это факт, а не угроза.
- Текст обязателен — статус не передаётся только цветом (доступность). Иконка и текст берутся из зоны, цвет — из `days_to_event`.
- Токены `--surface-3` и `--primary-container`/`--on-primary-container` для чипа C-07 больше не используются; они остаются за другими элементами (modal/dropdown и selected/tonal соответственно).

## 4. Маппинг данных API → визуальные токены

Вход для компонента C-07 — пара `{ status, days_to_event }` из ответа API. Разделение ответственности: **`status` задаёт иконку и текст** (§3.2), **`days_to_event` задаёт цвет** (§4.1).

| status | days_to_event | Иконка / текст (по зоне) | Цвет | Подложка |
|---|---|---|---|---|
| `no_date` | `null` | `event_busy` / «нет даты» | `--on-surface-variant` | `--neutral-chip` |
| `far` | > 14 | `schedule` / «{days_to_event} дн.» | `--success` | `--success-container` |
| `near` | T < N ≤ 14 | `event_upcoming` / «{days_to_event} дн.» | `--success` при N > 7; `--warn` при N ≤ 7 | `--success-container` / `--warn-container` |
| `hot` | 1 ≤ N ≤ T | `warning` / «осталось {days_to_event} дн.» | `--warn` при N ≤ 7; `--success` при N > 7 | `--warn-container` / `--success-container` |
| `critical` | 0 | `priority_high` / «сегодня!» | `--danger` | `--danger-container` |
| `past` | `null` | `event_available` / «прошла» | `--on-surface-muted` | `--surface-1` + граница `--outline-variant` |

### 4.1. Цвет по числу дней (токены)

Единственное правило выбора цвета. Столбец «возможные зоны» приведён для справки и на цвет не влияет.

| days_to_event | Возможные зоны | `color` (текст/иконка) | `container` (подложка) | Доп. |
|---|---|---|---|---|
| `0` | `critical` | `--danger` `#FF8A80` | `--danger-container` `#5C1F1B` | — |
| `1..7` | `hot`; `near` при `T < 7` | `--warn` `#FFD54F` | `--warn-container` `#4A3C12` | — |
| `> 7` | `near`, `far`; `hot` при `T > 7` | `--success` `#7FD9A6` | `--success-container` `#1F3D2E` | — |
| `past` / `< 0` | `past` | `--on-surface-muted` `#8E8B96` | `--surface-1` `#1D1D20` | граница 1px `--outline-variant` |
| `null` | `no_date` | `--on-surface-variant` `#C9C5CF` | `--neutral-chip` `#3A3A40` | — |

Правила:
- Число дней фронтенд берёт из `days_to_event` как есть, без собственного пересчёта от дат.
- Граница «горячей» зоны персональна (T из `threshold_days` сторожка): фронтенд не знает T и не обязан — сервер уже поместил сторожок в нужную зону. UI только отображает. Цвет же от T не зависит: порог недели — константа UI (7 суток), а не пользовательская настройка.
- **Карточка календаря S1** (собрание может не быть сторожком): локальная оценка зоны по `days_to_event` с порогами по умолчанию (T=7, S=14) допустима для отображения, но как только тикер становится сторожком, источник истины — серверный `status`. Правило цвета (§4.1) одинаково для S1 и S2.
- Если `days_to_event = null`, цвет нейтральный, кроме `status = past` (приглушённый). Порядок проверки — как в §3.1.

## 5. Формат текста по числу дней

- 1 день — «1 день», 2–4 — «N дня», 5–20 — «N дней», дальше по правилам русской плюрализации (21 день, 22 дня, 25 дней и т.д.).
- В `critical` дата совпадает с текущей — текст фиксированный «сегодня!» (без счётчика).
- `past`: подпись «прошла»; tooltip (десктоп, hover) не показывается — в этом статусе API отдаёт `next_record_date = null` и `days_to_event = null`, прошедшие события в ответ сторожка не включаются. Если прошедшая дата нужна в деталях, её берут отдельным запросом (`/record-dates?to=<today>` для отсечек, `/meetings?from&to` для собраний), а не из строки сторожка.

## 6. Поведение при отсутствии данных

- Нет ни отсечки, ни собрания с вопросом о дивидендах → зона `no_date`: нейтральный чип, в строке сторожка дата «не объявлена». При появлении даты (обновление данных) UI переключает зону по серверному статусу автоматически; подсветить изменение краткой анимацией (pulse 300 мс на чипе) при смене на `hot`/`critical`.
- Дата собрания известна, отсечка не объявлена → это **не** `no_date`: сервер выбирает собрание как событие сторожка (fallback), зона датированная (`far`/`near`/`hot`/`critical`), чип показывает число дней до собрания. В ячейке «Отсечка» — дата собрания (`next_record_date` = `next_meeting_date`). В деталях собрания — пояснение «Дата закрытия реестра будет объявлена позже; показана дата собрания».
- Прошедшее событие, будущих нет → `past`: чип «прошла», `next_record_date` и `days_to_event` в ответе `null` (прошедшие события в ответ сторожка не включаются).
- Ошибка загрузки свежих данных дополняется баннером «данные могли устареть» поверх старого отображения (C-13); цвета зон не меняются. Метка «обновлено N минут назад» строится по полю `fetched_at` соответствующих записей (поле добавляется в API по решению Р-6); **при отсутствии `fetched_at` в ответе метка не отображается**.

## 7. Сортировка и приоритеты в списках

- S2 (сторожки): сверху `critical`, `hot`, `near`, `far` (по возрастанию дней внутри зоны), затем `no_date`, в конце — `past`.
- S1 (календарь): внутри выбранного периода сортировка по дате собрания; зоны на порядок не влияют (цвет чипа определяется числом дней, §3.1).

## 10. DSI не является индикатором срока

Бейдж DSI (C-16) — отдельная дивидендная характеристика, а не зона шкалы `no_date/far/near/hot/critical/past`. Он не влияет на цвет чипа C-07, сортировку и бейдж-счётчик AppBar; его подсказка описана в [2026-10-20_dividend-metrics_ui.md](./2026-10-20_dividend-metrics_ui.md).

## 11. Снятые вопросы

В C-01 (AppBar) и C-02 (BottomNav) добавлен бейдж-счётчик сторожков в статусах `hot`/`critical`: нейтральная плашка `--warn-container`/`--warn`, скрыт при 0 и до первой загрузки списка сторожков; клиентского пересчёта нет — значение строится по серверным `status` из `GET /api/v1/watchlist`. Индикация внутри экранов (C-07 + сортировка §7) сохраняется как основная; бейдж — глобальный «маячок» вне экрана S2.
