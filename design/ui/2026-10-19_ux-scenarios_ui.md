# UX-сценарии MVP «Дивидендный календарь»

Дата: 2026-10-19
Область: ui
Статус: согласуется с system-designer

## Базовые понятия

- **Тикер** — акция Московской биржи (например, SBER, GAZP).
- **Собрание акционеров** — заседание, в повестке которого есть вопрос о выплате дивидендов.
- **Дата отсечки** — дата закрытия реестра акционеров, имеющих право на дивиденды.
- **Сторожок** — установленное пользователем отслеживание выбранного тикера до наступления даты отсечки.

## Участники и предположения

- Пользователь MVP — непрофессиональный инвестор, авторизация/аккаунты в MVP минимальны (локальный пользователь/один профиль). UX не зависит от механики регистрации.
- Данные о собраниях и отсечках поступают из бэкенда и обновляются автоматически; UI не управляет источниками данных.

## Сценарий 1. Просмотр календаря собраний и дат отсечки

**Цель:** быстро понять, какие собрания с вопросами о дивидендах намечены и когда по ним отсечка.

**Вход:** пользователь открывает приложение (экран «Календарь» — стартовый роут).

**Шаги:**
1. Пользователь открывает экран «Календарь».
2. Экран запрашивает у API список собраний (в пределах ближайшего окна по умолчанию: от сегодня и на 3 месяца вперёд, плюс прошедшие за последний месяц).
3. Приложение показывает сетку/список карточек собраний: тикер, эмитент, дата собрания, дата отсечки, маркер срока до отсечки.
4. Пользователь фильтрует/листает по месяцам (переключение месяца или скролл ленты).
5. По клику на карточку — раскрывается детальный вид собрания: дата собрания, дата отсечки, вопрос о дивидендах в повестке, статус сторожка по тикеру, ссылка на первоисточник. Суммы дивидендов не показываются — в MVP они не моделируются и не собираются (backend/API таких полей не предоставляет).
6. Опционально пользователь переходит на страницу пользователя, чтобы поставить «сторожок» на интересующий тикер.

**Состояния сценария:**

| Состояние | Что видит пользователь | Поведение UI |
|---|---|---|
| Загрузка | Скелетоны карточек / индикатор в шапке | Блокируются фильтры, пока не получены данные |
| Пусто | Текст «В выбранном периоде собраний нет» + подсказка сменить месяц | Предложить перейти к следующему месяцу кнопкой «Далее» |
| Ошибка API | Баннер ошибки с сообщением и кнопкой «Повторить» | Данные не очищаются, если часть уже была загружена (stale-карточки помечаются серым) |
| Норма | Список карточек с понятными сроками | По умолчанию сортировка: сначала предстоящие, затем прошедшие |

**Результат:** пользователь понимает ближайшие окна отсечек по всем тикерам рынка.

## Сценарий 2. Поиск/выбор тикера и постановка «сторожка»

**Цель:** добавить тикер в личный список отслеживания, чтобы UI наглядно показывал приближение его отсечки.

**Вход:** пользователь на «Странице пользователя».

**Шаги:**
1. Пользователь фокусируется в поле поиска «Найти тикер».
2. Вводит фрагмент тикера или названия эмитента (кириллицей/латиницей, регистронезависимо).
3. UI с дебаунсом запрашивает у API подсказки и показывает выпадающий список: тикер, краткое имя эмитента.
4. Пользователь выбирает тикер (клик/Enter/стрелки+Enter).
5. Тикер добавляется в список «Мои сторожки» с начальным статусом по последней известной дате отсечки:
   - если дата уже известна — сразу рассчитывается индикатор срока (см. «индикация-сроков»);
   - если даты нет — статус «Дата отсечки не объявлена» (серый индикатор).
6. Появляется snackbar-подтверждение «Сторожок установлен для SBER».

**Состояния сценария:**

| Состояние | Что видит пользователь | Поведение UI |
|---|---|---|
| Пустой ввод | Подсказка «Начните вводить тикер или название» | Dropdown скрыт |
| Ничего не найдено | Текст «Тикер не найден» + совет проверить написание | Кнопки «добавить» нет, опасности дубля нет |
| Дубликат | Строка тикера в подсказках помечена «Уже отслеживается» | Кнопка добавления disabled |
| Загрузка подсказок | Спиннер в dropdown, «Ищем…» | Enter игнорируется, пока нет списка |
| Ошибка поиска/добавления | Snackbar «Не удалось добавить. Повторить?» | Пользовательский выбор остаётся в поле, повторная попытка по кнопке |

**Результат:** тикер сохранён как «сторожок» и виден в списке с актуальным сроком до отсечки.

## Сценарий 3. Снятие «сторожка»

**Цель:** убрать тикер из отслеживания.

**Вход:** страница пользователя, список «Мои сторожки».

**Шаги:**
1. Пользователь в строке сторожка жмёт кнопку «Снять» (иконка-корзина/крестик на чипе).
2. UI запрашивает подтверждение только если серверный статус сторожка — `hot` или `critical` (снятие в «горячей» зоне критично). Порог `hot` персонален (`threshold_days` сторожка), поэтому условие привязано к статусу из API, а не к числу дней на клиенте. Иначе снимает мгновенно.
3. При подтверждении — DELETE на API, элемент плавно исчезает, показывается snackbar «Сторожок по SBER снят» с кнопкой «Отменить» (undo 5 сек).
4. Undo возвращает элемент в том же состоянии (повторный POST).

**Состояния сценария:**

| Состояние | Что видит пользователь | Поведение UI |
|---|---|---|
| Успех | Snackbar + undo | Элемент удалён из списка |
| Ошибка API | Snackbar «Не удалось снять. Повторить?» | Строка остаётся, кнопка «Снять» доступна повторно |
| Дата прошла | Подтверждение не требуется | Сразу удаление |

**Результат:** тикер больше не отслеживается; пользователь не теряет случайно важный сторожок без подтверждения.

## Сценарий 4. Просмотр списка «сторожков» с индикацией приближения даты

**Цель:** одним взглядом оценить, по каким тикерам отсечка приближается.

**Вход:** страница пользователя (дефолтный вид списка «Мои сторожки»).

**Шаги:**
1. Пользователь открывает страницу.
2. Список сторожков загружается, сортировка по умолчанию: ближайшая отсечка сверху; сторожка без даты — в конце.
3. Для каждой строки показывается: тикер, имя эмитента, дата отсечки (или «не объявлена»), счётчик дней, индикатор срока (цвет/иконка/подпись по шкале из «индикация-сроков»).
4. Пользователь фильтрует по статусам («все», «горячие» — записи со статусом `hot`/`critical` по канонической шкале, «без даты», «прошла»). Фиксированной границы «N дней» нет: «горячая» зона персональна (`threshold_days` сторожка), поэтому фильтр привязан к серверному статусу.
5. При желании — переходит по тикеру в календарь (экран «Календарь» фокусируется на нужной карточке собрания).

**Состояния сценария:**

| Состояние | Что видит пользователь | Поведение UI |
|---|---|---|
| Пусто | Иллюстрация/подсказка «Добавьте первый сторожок» + кнопка-фокус на поле поиска | Кнопка переводит курсор на поиск (см. сценарий 2) |
| Загрузка | Скелетоны строк | Блокировка сортировки/фильтров |
| Ошибка | Баннер + кнопка «Повторить» | Сохранить последний успешный список с пометкой «данные могли устареть» |
| Есть прошедшие даты | Строка серым с пометкой «прошла» | Рекомендация снять сторожок |

**Результат:** статус каждого сторожка считывается мгновенно, приоритеты понятны.

## Общие состояния приложения

| Состояние | Где применяется | Требование UI |
|---|---|---|
| First-load (холодный старт) | оба экрана | Полоса прогресса в AppBar, content-area в скелетонах |
| Pull-to-refresh / кнопка обновления | оба экрана | Индикатор поверх контента, без перезагрузки страницы |
| Отсутствие сети | оба экрана | Баннер «Нет соединения» + повтор автоматически с ростом задержки |
| Истёкшие данные | оба экрана | Плашка «Обновлено N минут назад» |

## Источники данных для мета-индикации

- Метка «Обновлено N минут назад» строится по полю `fetched_at` соответствующих записей API (минимум по показанному набору; поле добавляется в контракт по решению Р-6). При отсутствии `fetched_at` в ответе метка скрывается — интерфейс не показывает устаревшую по смыслу подсказку.
- Ссылка «Источник: раскрытие эмитента» в деталях собрания (S1.1) ведёт на `source_url` собрания. При отсутствии `source_url` ссылка скрыта; остальные детали (даты, повестка, статус сторожка) отображаются как обычно.

## Снятые с повестки вопросы (вне MVP, решение Р-5)

- Личный кабинет с авторизацией — вне объёма MVP: сторожки хранятся для одного «локального» пользователя/профиля (см. «Участники и предположения»).
- Push-уведомления о приближении отсечки — вне объёма MVP: MVP ограничен индикацией в интерфейсе.
