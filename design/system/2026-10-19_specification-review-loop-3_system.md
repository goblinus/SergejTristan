# 2026-10-19 — Ревью спецификаций областей, раунд 3 (system)

> Актуальность: документ исторический. Изменение от 2026-10-20 (дивидендные метрики, [ADR-0005](./adr/2026-10-20_adr-0005-dividend-metrics_system.md)) частично пересматривает решение Р-5 в части периода, суммы на акцию, доходности и DSI.

## Назначение документа

Протокол финального ревью спецификаций областей `ui`, `frontend`, `backend` (раунд 3 из 3): верификация выполнения задач раунда 2, итоговая проверка консистентности модели данных, API-контрактов и UX-сценариев, вердикт о согласовании комплекта проектной документации MVP.

## Вердикт

**Согласовано (approved = true).** Все задачи раунда 2 выполнены тремя областями; перекрёстных противоречий по терминам, DTO, статусам, маршрутам и сортировкам не осталось; открытые вопросы во всех спецификациях закрыты ссылками на решения Р-1..Р-10. Критерии согласования раунда 3 (см. протокол раунда 2) выполнены полностью. Комплект документации MVP «Дивидендный календарь» готов как вход для разработки.

## Проверка задач раунда 2

### backend — выполнено

1. **api-контракт** (`GET /api/v1/watchlist`): правило сортировки приведено к Р-7 — датированные сторожки по `next_record_date` ASC, затем `no_date`, затем `past`; NULL-блок разделён на две группы, указан составной ключ сортировки (`status_rank`, `next_record_date`, `ticker`). Документ правил расчёта статуса содержит зеркальный раздел «Сортировка списка сторожков» с тем же каноническим порядком и ссылкой на §7 `design/ui/2026-10-19_dates-indicators_ui.md`.
2. **api-контракт**: эндпоинт `GET /api/v1/tickers/{ticker}` и `upcoming_meetings` удалены (Р-8); сводная таблица содержит 7 эндпоинтов без карточки тикера; структура роутеров в `архитектура-бэкенда` синхронизирована (`app/api/tickers.py` — «только список; карточка тикера исключена из MVP, решение Р-8»).

### frontend — выполнено

1. **типы-и-api-клиент**: `GET /tickers/{ticker}` и тип `TickerDetails` упразднены с явной ссылкой на Р-8; открытый вопрос №1 закрыт решением Р-10 (порт 8000, base path `/api/v1`, Vite-proxy `/api` → `http://localhost:8000`), вопрос №2 отменён вместе с эндпоинтом. Таблица эндпоинтов соответствует контракту backend один в один.
2. **управление-состоянием**: порядок списка сторожков приведён к Р-7 (серверный канонический порядок: датированные по возрастанию `next_record_date` → `no_date` → `past`).
3. **архитектура + компонентная-схема (puml)**: бейдж-счётчик `hot`/`critical` добавлен в AppHeader (C-01) и BottomNav (C-02) по Р-9: `computed` по `useWatchlist().items`, скрыт при 0 и до загрузки списка, без отдельных запросов; открытый вопрос №1 закрыт ссылкой на Р-9.
4. **сборка-и-инструменты**: устаревшее утверждение о пустом каталоге ADR убрано; дана ссылка на действующие ADR-0001..0004, документ позиционирован как детализация ADR-0004.

### ui — выполнено

1. **состав-ui-кита (C-01, C-02)**: бейдж-счётчик сторожков `hot`/`critical` описан по Р-9 (плашка `--warn-container`/`--warn`, скрыт при 0 и до загрузки списка; для C-02 — стандартное Material-положение badge). Вайрфреймы S1/S2 дополнены позицией бейджа на вкладке «Мои сторожки» (●3).
2. **индикация-сроков**: раздел «Открытые вопросы» переименован в «Снятые вопросы», вопрос §9 закрыт решением Р-9 с полным описанием правил бейджа.

## Итоговая перекрёстная проверка (раунд 3)

- **Модель данных**: каноническая ER-модель system и схема БД backend согласованы (Р-2): `tickers`, `shareholder_meetings`, `record_dates` (прямой `ticker_id`, NULL-able `meeting_id`, `kind`), `watchlist_items` (`threshold_days`, `created_at`). DTO фронтенда зеркалят Pydantic-схемы контракта (`snake_case`, конверт `Page`, `fetched_at`, `source_url`).
- **Шкала статусов**: единое множество `{no_date, far, near, hot, critical, past}` идентично в контракте backend, правилах расчёта, типах frontend (`WatchStatus`) и сводной таблице ui (§8, машиночитаемый маппинг). Пороги: `T = threshold_days` (по умолчанию 7), граница `near` = 14 (`DIVCAL_WATCH_SOON_DAYS`). Старые обозначения (`ok/soon/due`, префиксы `d-`) в действующих документах отсутствуют.
- **API-контракт ↔ UX**: все потребности ui/frontend покрыты: `GET /meetings/{id}` — deep-link модала `?meeting=<id>`; `GET /record-dates` — отсечки без собрания в календаре; `fetched_at` — индикатор свежести; `source_url` — ссылка на источник в S1.1; идемпотентный `POST /watchlist` — undo в Snackbar; сортировка watchlist — канонический порядок S2. Обратных зависимостей без поставщика нет: каждый эндпоинт контракта имеет потребителя (удалённый `GET /tickers/{ticker}` — подтверждение границы MVP, Р-8).
- **Маршруты и навигация**: ui (карта экранов, `design/ui/2026-10-19_navigation_ui.puml`) и frontend (роутинг) согласованы: `/calendar` (редирект `/`), `/me`, модал через query; отдельных страниц собрания/эмитента нет.
- **Объём MVP**: избыточной функциональности не осталось — суммы дивидендов, `last_trading_day`, экран карточки эмитента, авторизация, уведомления, настройка порога через UI последовательно исключены или отложены во всех трёх областях (Р-5, Р-8). Бейдж-счётчик принят в MVP решением Р-9 и реализован согласованно (ui-кит, wireframes, frontend-архитектура, компонентная схема).
- **Окружение**: порт 8000 / base path `/api/v1` / Vite-proxy согласованы между backend (зависимости-и-окружение) и frontend (Р-10).
- **Открытые вопросы**: во всех действующих спецификациях областей разделы открытых вопросов пусты или переименованы в «снятые», со ссылками на решения Р-1..Р-10.

## Несущественное наблюдение (не блокирует согласование)

- В `design/backend/2026-10-19_architecture_backend.md` комментарий к `app/api/meetings.py` («GET /meetings») не перечисляет `GET /meetings/{id}`. Это косметика комментария в дереве файлов: контракт (`api-контракт`), роутер-таблица frontend и сценарий deep-link описывают эндпоинт корректно и однозначно. Поправить при первом же касании документа в разработке.

## Закрытие процесса проектирования

Трёхраундовый цикл согласования завершён. Дальнейшие изменения спецификаций — только через новые ADR (design/system/adr/) либо новым ревью system-designer при появлении потребностей за границами MVP (карточка эмитента, суммы дивидендов, уведомления, мультипользовательность).
