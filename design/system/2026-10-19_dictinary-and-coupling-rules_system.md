# 2026-10-19 — Глоссарий и правила стыковки областей (system)

Обновлён: 2026-10-19 (ревью, раунд 2) — термины приведены к решениям Р-1..Р-6 протокола раунда 1: `record_date` вместо `cutoff_date`, таблица `record_dates` вместо `record_cutoffs`, `watchlist_items`/`/watchlist` вместо `watchers`/`/api/watchers`, каноническая шкала статусов сторожка из шести значений (расчёт на сервере), префикс API `/api/v1`.

## Назначение документа

Единая терминология (русская и английская для именования в коде/API), правила форматов данных и процесс согласования спецификаций между областями `ui`, `frontend`, `backend`. Источник истины по терминам — при расхождениях документы областей правятся под этот глоссарий.

## 1. Глоссарий предметной области

| Термин (RU) | Термин для кода/API (EN) | Определение |
|---|---|---|
| Тикер | `ticker` | Торговый код акции на Мосбирже (например, SBER). Верхний регистр, без пробелов. |
| Эмитент | `issuer` | Юридическое лицо, выпустившее акцию. В MVP представлено полями `tickers.short_name`/`full_name` (отдельной сущности нет). |
| Собрание акционеров | `shareholder_meeting` (таблица `shareholder_meetings`) | Собрание, на повестке которого — вопрос о выплате дивидендов (признак `dividend_question`). |
| Повестка | `agenda` | Перечень вопросов собрания. В MVP — булев признак `dividend_question` + свободный текст `description`. |
| Дивидендная отсечка (отсечка) | `record_date` (таблица `record_dates`, колонка `record_date`) | Дата, на которую определяется список лиц, имеющих право на дивиденды (вид `kind = dividend_payment`). В контексте Мосбиржи совпадает с датой закрытия реестра (режим T+1 для реестров по дивидендам). Термины «отсечка» и «закрытие реестра» в MVP используются как синонимы; в коде/API — только `record_date`. |
| Отсечка для участия в собрании | `record_date` с `kind = meeting_participation` | Закрытие реестра для участия (голосования) в собрании. Сторожки не отслеживают этот вид. |
| Закрытие реестра | `record_date` | Дата фиксации реестра акционеров. См. «отсечка». |
| Сторожок | `watchlist_item` (таблица `watchlist_items`, ресурс `/api/v1/watchlist`) | Настройка пользователя: тикер + порог приближения (`threshold_days`). Отслеживание ближайшей будущей отсечки `dividend_payment` по тикеру. |
| Порог приближения | `threshold_days` | Число календарных дней до отсечки, определяющее границу «горячей» зоны сторожка (статус `hot`). По умолчанию 7, диапазон 1..365. |
| Источник данных | `source` / `source_url` | Внешний сайт (moex.com, disclosure.ru и пр.), откуда получена запись. |
| Нормализация | `normalize` / `normalization` | Приведение сырых данных источника к канонической модели (форматы дат, кодировка UTF-8, регистр тикеров). Выполняется только в collectors. |
| Сбор данных | `ingest` / `collect` | Процесс извлечения -> нормализации -> upsert в БД. |

**Статусы сторожка** (каноническая шкала, решение Р-4; вычисляются на сервере в API при чтении `GET /api/v1/watchlist`, в БД не хранятся; D — дней до ближайшей будущей `record_date` от текущей даты сервера, T — `threshold_days` сторожка, S — `DIVCAL_WATCH_SOON_DAYS`, по умолчанию 14):

| Статус (код) | RU | Условие |
|---|---|---|
| `no_date` | Дата неизвестна | У тикера нет записей отсечки `dividend_payment` |
| `far` | Далеко | D > S |
| `near` | Приближается | T < D ≤ S |
| `hot` | Горячий срок | 1 ≤ D ≤ T |
| `critical` | Сегодня | D = 0 |
| `past` | Прошла | Будущих отсечек нет, есть прошедшие |

## 2. Правила форматов данных

### Даты и время

- **Доменные даты** (`meeting_date`, `record_date`): календарная дата без времени, семантика московского времени (UTC+3).
  - БД: `DATE`.
  - JSON/API и TypeScript: строка ISO 8601 `YYYY-MM-DD` (без `T`, без часового пояса).
- **Технические метки** (`fetched_at`, `created_at`): момент времени в **UTC**.
  - БД: `TIMESTAMP` (UTC; для SQLite — дисциплина приложения, см. ADR-0001).
  - JSON/API: ISO 8601 с суффиксом `Z` (например, `2026-10-19T06:00:00Z`).
- «Сегодня» для расчёта статуса сторожка — текущая календарная дата **сервера** API (расчёт на сервере, решение Р-3; см. `design/backend/2026-10-19_alarm-date-calculation-rules_backend.md`).

### Идентификаторы и строки

- `ticker` — верхний регистр, латиница, `VARCHAR(12)`, без пробелов.
- Кодировка всех текстов и файлов проекта — **UTF-8** (включая ответы источников: нормализация в collectors).
- URL источников (`source_url`) — абсолютные, как получены из источника.

### API

- Формат: JSON, префикс пути `/api/v1` (версия MVP — v1; решение Р-1).
- Имена полей DTO совпадают с именами колонок канонической модели (snake_case); мэппинг кейсов на клиенте не применяется.
- Списковые ответы — конверт `Page { items, page, page_size, total }`.
- OpenAPI генерируется FastAPI из Pydantic-моделей (ADR-0002) — источник правды контракта.

## 3. Правила версионирования документов

- Имя файла: `ГГГГ-ММ-ДД_название-документа_<область>.md` — дата в имени **создания**, не обновляется.
- Содержательные правки существующего документа: изменения вносятся в тот же файл, в начало документа добавляется/обновляется строка «Обновлён: ГГГГ-ММ-ДД — кратко что изменено».
- ADR не переписываются задним числом: отмена/изменение решения — новый ADR со статусом «Отменяет ADR-XXXX»; старый получает статус «Заменён (ADR-YYYY)».
- Статусы ADR: `Предложено`, `Принято`, `Заменён (ссылка)`, `Отклонён`.

## 4. Процесс ревью и стыковки спецификаций

1. **Областные дизайнеры** (`ui`, `frontend`, `backend`) готовят спецификации в своих директориях `design/<область>/`, опираясь на документы `design/system/` (обзор, контейнеры, ER-модель, ADR, глоссарий).
2. **Системный дизайнер** (system) ревьюит спецификации на соответствие:
   - терминологии глоссария и форматам дат/полей ER-модели;
   - границам MVP и правилам разделения ответственности (писатели/читатели);
   - принятым ADR (если спецификация нарушает ADR — нужен либо пересмотр спецификации, либо новый ADR).
3. Результат ревью: замечания к спецификации либо согласование. Противоречия между областями разрешает системный дизайнер; при затрагивании системных решений — правка соответствующего документа `design/system/` с записью обновления (п. 3).
4. Точки стыковки, требующие парного согласования областей (обе стороны фиксируют одну и ту же договорённость):
   - `backend` <-> `frontend`: состав эндпоинтов (`/api/v1/tickers`, `/api/v1/meetings`, `/api/v1/record-dates`, `/api/v1/watchlist`), схемы DTO, семантика ошибок (`{"detail": ...}`), конверт пагинации `Page`;
   - `ui` <-> `frontend`: визуальные состояния сторожка по канонической шкале (`no_date/far/near/hot/critical/past`) и отображение дат;
   - `backend` (collectors) <-> `system`: любое изменение бизнес-ключей или состава полей источников требует правки ER-модели.
