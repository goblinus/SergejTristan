# 2026-10-19 — Контейнеры и потоки данных (system)

Обновлён: 2026-10-19 (ревью, раунд 2) — расчёт статуса сторожка перенесён из клиента в API (решение Р-3); имена эндпоинтов приведены к контракту backend (`/api/v1/tickers`, `/api/v1/meetings`, `/api/v1/record-dates`, `/api/v1/watchlist`); шкала статусов — каноническая (Р-4).

## Назначение документа

Контейнерный уровень архитектуры MVP: состав контейнеров (в терминах C4 — развёртываемых/запускаемых единиц), их ответственность и три ключевых потока данных. Документ отвечает на вопросы: кто пишет/читает какие данные, где происходит нормализация, где вычисляется близость даты отсечки.

См. диаграмму: [2026-10-19_контейнеры_system.puml](./2026-10-19_контейнеры_system.puml).

| Контейнер | Технологии | Ответственность | Запуск |
|---|---|---|---|

## Потоки данных

### Поток 1: Обновление данных (collectors -> БД)

```
источники (moex.com, disclosure.ru) -> извлечение (fetch) -> нормализация (parse/mapping)
  -> upsert в БД (по бизнес-ключу) -> отметка fetched_at/source_url
  -> отдельный проход: история дивидендов MOEX -> DSI в tickers.dsi
```

- **Нормализация выполняется только в скриптах**, до записи в БД. API и фронтенд работают с уже нормализованными данными.
- **Дивидендные метрики (ADR-0005):** период и сумма на акцию пишутся в собрание; DSI — снапшот в тикере, пересчитывается скриптом сбора; доходность на чтении вычисляет API из суммы и последней цены.
- Идемпотентность: повторный запуск по тем же входным данным не создаёт дублей — upsert по бизнес-ключам (тикер; ticker+дата+вопрос собрания; и т.д., см. ER-модель).
- Трассировка: каждая запись несёт `source_url` и `fetched_at` (ADR-0003).
- Сырые ответы источников на диске (кэш/аудит) — опционально, вне MVP-гарантий.

### Поток 2: Чтение данных пользователем (frontend -> API -> БД)

```
пользователь -> SPA -> GET /api/... -> Backend API (SQLAlchemy -> БД)
  -> DTO (Pydantic) -> JSON -> SPA -> рендер календаря/списков
```

- Доменные эндпоинты — **только чтение** (GET). Изменение доменных данных через API запрещено.
- DTO собрания и сторожка содержат дивидендные метрики (`dividend { period, amount_per_share, yield_percent }`, `dsi`, `next_dividend`) и `logo_url` эмитента (ADR-0005, ADR-0006).
- Минимальный набор (детализация — в backend-спецификации `2026-10-19_api-контракт_backend.md`):
  - `GET /api/v1/tickers` — список тикеров (поиск `q`, пагинация `Page`);
  - `GET /api/v1/meetings?from&to&ticker` — календарь собраний с вложенной отсечкой;
  - `GET /api/v1/meetings/{id}` — карточка собрания (deep-link модала деталей);
  - `GET /api/v1/record-dates?from&to&ticker&kind` — календарь отсечек (включая отсечки без связанного собрания).

### Поток 3: Сторожок (frontend -> API -> БД; расчёт статуса — на сервере, решение Р-3)

```
пользователь: выбор тикера -> SPA -> POST/DELETE /api/v1/watchlist -> БД (upsert/delete)
пользователь: просмотр -> SPA -> GET /api/v1/watchlist -> Backend -> БД
  -> JSON (ticker, threshold_days, next_record_date, days_to_cutoff, status,
          next_dividend, dsi) -> SPA
  -> отображение статуса по канонической шкале, без пересчёта на клиенте
```

**Решение о размещении расчёта статуса сторожка (пересмотрено на ревью, раунд 1, Р-3):** вычисляется **в API на чтении** (`GET /api/v1/watchlist`) от текущей даты сервера. Обоснование:
- единая точка правил (пороги `threshold_days` и `DIVCAL_WATCH_SOON_DAYS`) — нет риска рассинхрона логики клиента и сервера;
- фронтенд упрощается до отображения готовой пары `{ status, days_to_cutoff }` (маппинг в визуальные токены — компонент ui `DeadlineIndicator`);
- нагрузка MVP (один пользователь, десятки сторожков) позволяет расчёт на каждый запрос.

Бэкенд возвращает `next_record_date`, `days_to_cutoff`, `status` по канонической шкале из шести значений (`no_date/far/near/hot/critical/past`, решение Р-4). Статус — производное, в БД **не хранится**. Правила расчёта: `design/backend/2026-10-19_правила-расчёта-статуса-сторожка_backend.md`.

## Распределение ответственности (право записи)

| Сущность | Пишет | Читает |
|---|---|---|
| Тикер | collectors | API (-> SPA) |
| Собрание акционеров | collectors | API (-> SPA) |
| Дата отсечки | collectors | API (-> SPA) |
| Сторожок | API (по запросу SPA) | API (-> SPA) |

Единый писатель доменных данных — collectors; единый писатель пользовательских данных — API. Пересечений нет, конфликтов записи не ожидается.
