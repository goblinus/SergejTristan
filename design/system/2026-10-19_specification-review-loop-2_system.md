# 2026-10-19 — Ревью спецификаций областей, раунд 2 (system)

## Назначение документа

## Вердикт

**Не согласовано (approved = false).** Задачи раунда 1 для всех трёх областей выполнены, системные документы актуализированы самим system-designer (см. ниже). ## Новые решения system-designer (канон для доработки)

### Р-7. Сортировка списка сторожков (снимает противоречие backend vs ui)

Канонический порядок `GET /api/v1/watchlist` (ui `индикация-сроков`, §7):

1. все сторожки с известной отсечкой — по возрастанию `next_record_date` (эквивалентно зональному порядку `critical → hot → near → far`, т.к. зоны — смежные интервалы дней);
2. затем статус `no_date`;
3. затем статус `past`.

Текущее правило backend «`next_record_date` ASC, NULL в конце» смешивает `no_date` и `past` в хвосте — требует уточнения в API-контракте. Для датированных сторожков старый и новый порядок совпадают.

### Р-8. Эндпоинт `GET /api/v1/tickers/{ticker}` — вне MVP

Карточный эндпоинт тикера (`Ticker` + `upcoming_meetings`) не имеет потребителя: карта экранов ui явно исключает экран «Карточка эмитента», роутинг/композаблы frontend его не вызывают (автодополнение использует `GET /tickers?q`). По границам MVP эндпоинт исключается из контракта (вместе с типом `TickerDetails` на фронтенде). Возврат — только при появлении экрана-потребителя, новым согласованием.

### Р-9. Бейдж-счётчик «горячих» сторожков — принят в MVP

Закрывает открытый вопрос ui (`индикация-сроков`, §9) и frontend (`архитектура`, §8/1). Наличие бейджа с числом сторожков в статусе `hot`/`critical` на вкладке «Мои сторожки» (AppHeader C-01 и BottomNav C-02) — **в объёме MVP**: дёшево (computed по уже загруженному списку `useWatchlist`), полезно. Правила: скрыт при 0 и при незагруженном списке; число без цветовой семантики сверх нейтральной плашки `--warn-container`.

### Р-10. Порт и base path бэкенда в dev

Закрывает открытый вопрос frontend (`типы-и-api-клиент`, №1): порт бэкенда по умолчанию **8000** (`uvicorn ... :8000`, см. `design/backend/2026-10-19_dependencies-and-env_backend.md`), base path — `/api/v1`; Vite-proxy `/api` → `http://localhost:8000` сохраняет путь, корректно.

## Задачи по областям

### backend

1. **api-контракт** (`GET /api/v1/watchlist`): привести правило сортировки к Р-7 (датированные по `next_record_date` ASC → `no_date` → `past`); обновить текст и при необходимости примечания в документе правил расчёта статуса.
2. **api-контракт**: удалить `GET /api/v1/tickers/{ticker}` и описание `upcoming_meetings` (Р-8); синхронизировать сводную таблицу и структуру роутеров в `архитектура-бэкенда` (`app/api/tickers.py` оставляет только список).

### frontend

1. **типы-и-api-клиент**: удалить эндпоинт `GET /tickers/{ticker}` и тип `TickerDetails` (Р-8); закрыть открытые вопросы №1 (ответ — Р-10) и №2 (отменён вместе с эндпоинтом).
2. **управление-состоянием**: синхронизировать формулировку о порядке списка сторожков с Р-7 (серверный порядок: даты ASC → `no_date` → `past`).
3. **архитектура + puml**: добавить бейдж-счётчик `hot`/`critical` в AppHeader (C-01) и BottomNav (C-02) по Р-9 (computed по `useWatchlist().items`); закрыть открытый вопрос №1 ссылкой на Р-9.
4. **сборка-и-инструменты**: убрать устаревшее утверждение «design/system/adr/ пуст», сослаться на ADR-0001..0004 (ADR-0004 создан настоящим ревью), статус документа — согласован.

### ui

1. **состав-ui-кита (C-01, C-02)**: дописать бейдж-счётчик сторожков в `hot`/`critical` по Р-9 (скрыт при 0/до загрузки списка; нейтральная плашка); дополнить вайрфрейм S1/S2 позицией бейджа на вкладке.
2. **индикация-сроков**: снять открытый вопрос §9 как решённый (Р-9).

## Критерии согласования раунда 3

Раунд 3 признаётся согласованным, если: (а) задачи областей выше выполнены без новых расхождений; (б) перекрёстных противоречий по терминам, DTO, статусам, маршрутам и сортировкам не остаётся; (в) открытые вопросы во всех спецификациях закрыты ссылками на решения Р-1..Р-10.
