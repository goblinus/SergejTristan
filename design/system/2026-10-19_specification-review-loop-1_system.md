# 2026-10-19 — Ревью спецификаций областей, раунд 1 (system)

## Назначение документа

Протокол ревью спецификаций областей `ui`, `frontend`, `backend` (раунд 1 из 3): вердикт, принятые системные решения по противоречиям, задачи на доработку ответственным дизайнерам.

## Вердикт

**Не согласовано (approved = false).** Спецификации каждой области по отдельности полны и в рамках MVP, но между областями есть существенные рассинхроны: модель данных и терминология (backend vs каноническая ER-модель), API-контракт (backend vs frontend), шкала статусов сторожка (backend vs ui), карта экранов и компонентная модель (ui vs frontend). Все противоречия ниже разрешены решениями system-designer; задачи на доработку — в разделе «Задачи по областям».

## Что согласуется без замечаний

- Покрытие функциональности MVP полное: список тикеров, календарь собраний/отсечек, сторожки, страница пользователя, офлайн-сбор данных. Избыточной функциональности сверх объёма у backend нет (поля `board`/`lot_size`/`is_active` и второй `kind` отсечки приходят из тех же ответов источников — принимаются, см. решение Р-2).
- Backend: слоистая архитектура, Alembic, зависимости (uv), спецификация скриптов сбора, обработка недоступности источников — соответствуют контейнерам system и ADR-0001..0003.
- Frontend: слои, отказ от Pinia, toolchain (Vite/TS/ESLint/Prettier/Vitest), обработка ошибок `{detail}` — разумны и не противоречат system.
- UI: визуальный стиль (токены, типографика, доступность), состав UI-кита, вайрфреймы — в рамках MVP; мобильная компоновка зафиксирована (считается входящей в MVP, см. задачу frontend-4).

## Принятые решения system-designer (канон для доработки)

### Р-1. Терминология и имена в коде

За основу принимается фактически реализованный словарь backend-спецификаций (он уже согласован внутри backend-области и частично совпал у frontend):

- Дата отсечки в коде/API — `record_date` (таблица `record_dates`), а не `cutoff_date`. Глоссарий и каноническая ER-модель system будут обновлены (переименование термина; русский термин «отсечка» сохраняется).
- Сторожок: API-ресурс `/watchlist`, DTO `WatchlistItem`, таблица `watchlist_items`. Русский термин «сторожок» сохраняется.
- JSON-поля DTO — `snake_case` (как в API-контракте backend); camelCase-вариант frontend отклонён, мэппинг-кейс в `api/endpoints` не требуется.
- Префикс API `/api/v1` принимается (укладывается в правило `/api/` глоссария; версионирование не противоречит MVP).

### Р-2. Каноническая модель данных

Каноническая ER-модель приводится к уточнённой схеме backend (схема backend отражает реальные данные источников точнее первоначальной):

- `record_dates`: прямая связь `ticker_id`, опциональный `meeting_id` (NULL-able, ON DELETE SET NULL), колонка `kind` (`dividend_payment`/`meeting_participation`), бизнес-ключ `(ticker_id, record_date, kind)`. Допущение «1:1 собрание-отсечка» отменяется.
- `tickers`: `short_name`, `full_name`, `isin`, `board`, `lot_size`, `is_active` (soft-деактивация при исчезновении из листинга). Поле `sector` из первоначальной модели исключается (источник не даёт).
- `shareholder_meetings`: `meeting_type` (`annual`/`extraordinary`) + `dividend_question` + `description`; бизнес-ключ `(ticker_id, meeting_date, meeting_type)`.
- `watchlist_items`: `threshold_days` (1..365, по умолчанию 7), `created_at`; полей `source_url`/`fetched_at` нет.

### Р-3. Расчёт статуса сторожка — на сервере

Перенос расчёта из клиента (поток 3 контейнерной модели) в API **принимается**: единая точка правил, меньше логики на фронтенде, нагрузка MVP позволяет. Контейнерная модель system будет обновлена. API возвращает `next_record_date`, `days_to_cutoff`, `status`; фронтенд не пересчитывает.

### Р-4. Единая шкала статусов (снимает противоречие backend {ok/soon/due} vs ui {d-far…d-critical})

Каноническое множество статусов API — шесть значений, соответствующих зонам ui:

| status | Условие (D = дней до отсечки) |
|---|---|
| `no_date` | будущих отсечек нет и прошедших нет |
| `far` | D > 14 |
| `near` | T < D ≤ 14 |
| `hot` | 1 ≤ D ≤ T (T = `threshold_days` сторожка, по умолчанию 7; для карточек календаря без сторожка — T = 7) |
| `critical` | D = 0 |
| `past` | будущих нет, есть прошедшие |

`DIVCAL_WATCH_SOON_DAYS` (граница `near`) по умолчанию **14** (а не 30), общая для всех. Инвариант `T < 14`; при `T ≥ 14` зона `near` пуста, поведение корректно за счёт порядка проверок. Для карточек календаря (S1) зона считается по тем же правилам с T=7 и также может определяться фронтендом из `days`/дат — но сторожки всегда берут готовый `status` из API.

### Р-5. Границы MVP подтверждены

- Суммы дивидендов (рекомендованный дивиденд, доходность) — **вне MVP**: удаляются из DTO frontend и из ui-вайрфрейма/сценариев.
- Поле `last_trading_day` (учёт T+1) — вне MVP: удаляется из типов frontend.
- Пользовательская настройка `threshold_days` через интерфейс — вне ui MVP (поле остаётся в модели/API со значением по умолчанию; редактирование возможно позже через API).
- Авторизация, уведомления, мультипользовательность — вне MVP (подтверждено; открытые вопросы ui/frontend на эти темы закрыты).

### Р-6. Прочие стыковки

- Эндпоинт `GET /api/v1/meetings/{id}` добавляется в контракт backend (нужен deep-link модалу деталей `?meeting=<id>` после перезагрузки).
- В DTO `Ticker`/`Meeting`/`RecordDate` добавляется `fetched_at` (индикатор свежести «обновлено N минут назад» в ui); в `Meeting` добавляется `source_url` (ссылка на источник в деталях S1.1). Раннее решение backend «трассировка наружу не отдаётся» пересмотрено по требованию ui.
- Семантика `POST /watchlist` — идемпотентная (201 при создании, 200 при повторе с обновлением `threshold_days`); 409 не используется. `DELETE /watchlist/{ticker}` — по коду тикера.
- Все списковые ответы — конверт `Page {items, page, page_size, total}`.
- Отсечки без связанного собрания (`meeting_id IS NULL`) должны отображаться в календаре: фронтенд потребляет `GET /api/v1/record-dates` в дополнение к `/meetings`.
- Карта экранов — по ui: `/calendar` (с редиректом `/`), `/me`, детали собрания — модал `?meeting=<id>`, не отдельная страница. Отдельный маршрут `/meetings/:id` из роутинга frontend убирается (открытый вопрос frontend/ui закрыт решением ui).
- Мобильная компоновка (≤640px, BottomNav C-02) — **в объёме MVP** по ui-макетам.

## Задачи по областям

### backend

1. **api-контракт + правила расчёта статуса**: привести шкалу статусов к Р-4: значения `{no_date, far, near, hot, critical, past}` (вместо `ok/soon/due/past/no_date`), `DIVCAL_WATCH_SOON_DAYS` по умолчанию 14, семантика `hot` — интервал `1..T`. Обновить примеры, таблицу кодов, документ правил и комментарии в схеме БД («порог статуса»).
2. **api-контракт**: добавить `GET /api/v1/meetings/{id}` (200/404); добавить `fetched_at` в DTO `Ticker`/`Meeting`/`RecordDate` и `source_url` в `Meeting` (см. Р-6).
3. **схема-бд**: после переименования статусов синхронизировать формулировки (комментарий `threshold_days`). Состав таблиц менять не нужно — принят Р-2.

### frontend

1. **типы-и-api-клиент**: переписать DTO и эндпоинты строго по `design/backend/2026-10-19_api-contract_backend.md` с правками Р-4/Р-6: snake_case-поля (`ticker`, `short_name`, `meeting_date`, `meeting_type`, …), конверт `Page`, параметры `q`/`page`/`page_size`, тело POST `{ticker, threshold_days}`, идемпотентные 200/201, `DELETE /watchlist/{ticker}` по коду тикера. Убрать открытые вопросы №1–2 (решены: snake_case, `{detail}`).
2. **типы**: удалить `dividendAmount`/`dividendCurrency` и `lastTradingDay` (вне MVP, Р-5). `GET /meetings/{id}` оставить в списке эндпоинтов (Р-6), но без отдельной страницы.
3. **роутинг + архитектура**: синхронизировать с картой экранов ui (Р-6): маршруты `/calendar` (редирект с `/`) и `/me`; детали собрания — модал с `?meeting=<id>`, маршрут `/meetings/:id` убрать; навигация «Календарь»/«Мои сторожки». Компонентное дерево привести к ui-вайрфреймам: S1 — список/сетка карточек `MeetingCard` (месячный грид CalendarMonth/CalendarDay/EventChip исключён — ui-kit его явно не проектирует), фильтры месяца/прошедших, `UpcomingList` сохранить.
4. **архитектура/состояние**: добавить в дерево компонентов из ui-кита: `DeadlineIndicator` (C-07), `SnackBar` с undo при снятии сторожка (C-12; undo = повторный `POST /watchlist` — укладывается в идемпотентную семантику), модал деталей (C-08), `BottomNav` (C-02) и мобильную компоновку (в MVP, Р-6), офлайн-баннер и индикатор «обновлено N назад» (данные — из `fetched_at`, Р-6).
5. **темизация**: перейти на токены и значения из `design/ui/2026-10-19_visual-style_ui.md` (`--bg-base`, `--surface-0..4`, `--warn`/`--danger` и контейнеры), шрифт Inter (системный фолбэк), иконки Material Symbols Rounded. Имена `--color-*` из текущего документа не сохранять.
6. **композаблы**: `useCalendar` должен включать отсечки без собрания — добавить endpoint-модуль `record-dates.ts` (`GET /record-dates?from&to`) и объединить в проекции календаря/UpcomingList (Р-6).

### ui

1. **индикация-сроков**: привести шкалу к Р-4: идентификаторы зон = `{no_date, far, near, hot, critical, past}` (убрать префиксы `d-` и `no-date` → `no_date`), граница `hot` — переменная (порог сторожка, по умолчанию 7), `near` — до 14 дней. Описать маппинг «`status` + `days_to_cutoff` из API → визуальные токены»; JSON-сводку обновить. В сценарии 3 условие подтверждения снятия «≤ 7 дней» заменить на «статус `hot`/`critical`» (порог персональный).
2. **вайрфреймы + ux-сценарии**: убрать «Рекомендованный дивиденд» из модала S1.1 и упоминание планируемых дивидендов из сценария 1 (вне MVP, Р-5).
3. **ux-сценарии**: зафиксировать, что индикатор свежести («обновлено N минут назад») строится по `fetched_at` из API, а ссылка на источник в S1.1 — по `source_url` собрания (поля будут добавлены бэкендом, Р-6); описать поведение при отсутствии этих полей.
