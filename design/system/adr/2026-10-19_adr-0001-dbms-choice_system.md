# ADR-0001: Выбор СУБД для локального MVP

- Дата: 2026-10-19
- Статус: Принято
- Контекст: область system, MVP «Дивидендный календарь»

## Контекст и проблема

Для MVP требуется реляционная СУБД под сущности: Тикер, Собрание акционеров, Дата отсечки, Сторожок (см. каноническую ER-модель). Ограничения контекста:

- локальный запуск на одной машине (деплой вне рамок MVP);
- один пользователь, минимальная конкурентность записи;
- объём данных: сотни тикеров, порядка тысяч собраний/отсечек в год — малый объём;
- доступ из Python через SQLAlchemy (ORM + Core);
- писателей два класса: офлайн-скрипты сбора (upsert пакетами) и API (точечная запись сторожков) — не одновременно в доменных таблицах.

## Критерии выбора

1. Простота развёртывания и сопровождения на локальной машине (вес — высокий).
2. Достаточность для объёма и нагрузки MVP (вес — средний).
3. Совместимость и зрелость поддержки в SQLAlchemy (вес — средний).
4. Путь миграции на полноценную СУБД при выходе за рамки MVP (вес — низкий).

## Рассмотренные варианты

### SQLite

- (+) Нулевое развёртывание: файл БД, входит в Python; бэкап — копирование файла.
- (+) Полноценная поддержка в SQLAlchemy (диалект первого класса), включая `INSERT ... ON CONFLICT DO UPDATE` (upsert) — критично для ADR-0003.
- (+) Достаточная производительность для тысяч строк и единственного читателя/писателя.
- (-) Слабая поддержка конкурентной записи (write-lock на всю БД) — в MVP писатели разнесены по времени, не критично.
- (-) `TIMESTAMP(timezone=True)` хранится без tz — дисциплина UTC обеспечивается приложением.
- (-) Ограниченная эволюция схемы (ALTER TABLE урезан) — компенсируется Alembic-миграциями с batch-режимом.

### PostgreSQL

- (+) Строгая типизация дат/времени, полноценный DDL, конкурентная запись, готовность к масштабированию.
- (+) Знакома владельцу по основному стеку.
- (-) Требует установки и сопровождения сервера СУБД локально — избыточно для однопользовательского MVP.
- (-) Усложняет запуск pet-проекта (отдельный сервис, порты, креды).

## Решение

**MVP использует SQLite** (файл БД в директории проекта, подключение через SQLAlchemy URL `sqlite:///...`).

Сопутствующие решения:
- Включить `PRAGMA foreign_keys = ON` и `PRAGMA journal_mode = WAL` при подключении (целостность FK + параллельное чтение во время записи collectors).
- Даты/метки времени хранить по соглашениям из ER-модели (DATE без времени; моменты — в UTC, дисциплина на уровне приложения).
- Upsert через диалект `sqlite.insert(...).on_conflict_do_update`.
- Слой доступа к данным проектировать без SQLite-специфичных конструкций в бизнес-логике — замена строки подключения на PostgreSQL должна быть единственным изменением при масштабировании.

## Последствия

- Нулевая инфраструктура: проект запускается сразу после `uv sync`.
- Alembic-миграции — с batch-режимом для изменений схемы.
- При необходимости многопользовательности/деплоя принимается новый ADR о переходе на PostgreSQL (сроки пересмотра: при появлении требований из out-of-scope обзора архитектуры).

## Отклонённые альтернативы

- **PostgreSQL** — см. выше (избыточная инфраструктура для MVP).
- **Другие файловые/встраиваемые хранилища** (DuckDB, файлы JSON/CSV) — не рассматривались: доменная модель реляционная, требуется SQLAlchemy-совместимость и транзакции записи.
