# ADR-0003: Стратегия обновления данных в БД

- Дата: 2026-10-19
- Статус: Принято
- Контекст: область system, MVP «Дивидендный календарь»

## Контекст и проблема

Данные о тикерах, собраниях акционеров и датах отсечки поступают из внешних источников (moex.com, disclosure.ru и др.). Нужно определить:

- кто и когда выполняет сбор и запись (роли скриптов и API);
- как гарантировать отсутствие дублей и консистентность при повторных запусках;
- как обеспечить трассировку происхождения каждой записи.

См. также: контейнерная модель (поток 1), каноническая ER-модель.

## Рассмотренные варианты

### A. Офлайн-скрипты (запуск вручную или по расписанию ОС)

Отдельный Python-пакет в репозитории (`scripts`/collectors), запускаемый вручную или cron/Task Scheduler. Скрипты — единственный писатель доменных данных.

- (+) Простая эксплуатация, нет фоновых процессов внутри API; падение сбора не влияет на доступность API.
- (+) Лёгкая отладка: повторный запуск изолированной задачи.
- (-) Актуальность данных зависит от частоты запуска (принимается для MVP).

### B. Фоновые задачи внутри API-процесса (APScheduler/celery beat в том же runtime)

- (-) Усложняет API: жизненный цикл планировщика, блокировки, смешение ответственности (serve + ingest).
- (-) Фронтенд/API зависят от успешности фондовых задач.

## Решение

**Стратегия A:** офлайн-скрипты сбора, запуск вручную или по расписанию ОС. API-процесс фоновых задач не содержит (ADR-0002 это подтверждает: только обработка HTTP).

Дополнительные положения:

### Идемпотентность и upsert

- Все записи определяются **бизнес-ключами** (см. ER-модель): `tickers.ticker`; `(ticker_id, meeting_date)`; `record_cutoffs.meeting_id`.
- Запись выполняется как upsert (`INSERT ... ON CONFLICT DO UPDATE` в SQLite / PostgreSQL) по бизнес-ключу: вставка новой записи либо обновление изменившихся полей существующей.
- Повторный запуск скрипта над теми же входными данными не создаёт дублей и не меняет содержимое БД (кроме `fetched_at`).
- Запись скрипта — одна транзакция на пакет по источнику: частичная запись недопустима.

### Нормализация

- Нормализация (парсинг вёрстки/CSV/API ответа -> каноническая модель, приведение дат к `DATE`, текстов к UTF-8) происходит **в скриптах до записи**. БД хранит только нормализованные значения; API/frontend нормализацию не выполняют.

### Трассировка источника

- Каждая доменная запись содержит `source_url` (URL извещения/страницы источника) и `fetched_at` (UTC-момент загрузки). Обязательность полей определена в ER-модели (для `shareholder_meetings.source_url` — NOT NULL).
- Поля позволяют: аудит происхождения, выявление «протухших» записей по `fetched_at`, отладку парсеров.

### Удаление/устаревание

- Записи, исчезнувшие из источника, в MVP **не удаляются** — актуальность оценивается по `fetched_at`. Политика удаления — вопрос последующих итераций.

### Частота запуска

- Рекомендованный минимум: ежедневный запуск collectors до 09:00 по Мск (до перезагрузки страниц источников в течение дня). Конкретное расписание — эксплуатационная деталь, вне рамок проектной документации MVP.

## Последствия

- API остаётся простым read-only сервисом (кроме сторожков); SLA на сбор не зависит от SLA на обслуживание запросов.
- Требования к upsert и бизнес-ключам — обязательная часть backend-спецификации и тестовой стратегии collectors (повторный запуск эквивалентен первому).
- Права записи жёстко разведены: collectors — доменные таблицы; API — только `watchers`. Это исключает конфликты записи и упрощает рассуждение о консистентности.

## Отклонённые альтернативы

- Фоновые задачи в API-процессе — см. вариант B.
- ETL-инструменты (Airflow и т.п.) — избыточны для двух источников и одной машины.
