# ADR-0002: Выбор веб-фреймворка бэкенда (Python)

- Дата: 2026-10-19
- Статус: Принято
- Контекст: область system, MVP «Дивидендный календарь»

## Контекст и проблема

Необходимо выбрать Python-фреймворк для REST API MVP. Требования из архитектурного обзора:

- контракт с фронтендом — машиночитаемый (OpenAPI), SPA на Vue.js 3 потребляет JSON;
- стек уже зафиксирован проектом: SQLAlchemy + Pydantic, зависимости через uv;
- API компактный: read-only доменные эндпоинты + CRUD сторожков (см. контейнерную модель, потоки 2–3);
- приоритет — скорость разработки MVP и сопровождаемость.

## Критерии выбора

1. Нативная интеграция Pydantic (валидация и (де)сериализация DTO) — вес высокий.
2. Автоматическая генерация OpenAPI из кода (единый источник правды контракта) — вес высокий.
3. Скорость разработки MVP (объём шаблонного кода, DX) — вес средний.
4. Простота сопряжения с SQLAlchemy и uvicorn — вес средний.

## Рассмотренные варианты

### FastAPI

- (+) Pydantic — ядро фреймворка: модели запросов/ответов, валидация типов из коробки.
- (+) OpenAPI 3 генерируется из сигнатур хендлеров и Pydantic-моделей автоматически; встроенная Swagger UI/ReDoc для ручной проверки контракта.
- (+) ASGI (uvicorn), dependency injection, минимальный boilerplate для CRUD над SQLAlchemy.
- (-) Асинхронная модель требует дисциплины (sync def для SQLAlchemy-блокирующих вызовов) — для MVP с одним пользователем допустимы синхронные хендлеры в threadpool.

### Flask

- (+) Минимализм, зрелость, низкий порог входа.
- (-) Pydantic и OpenAPI — через сторонние расширения (flask-pydantic, flasgger, apispec): контракт и валидация не «из коробки», риск расхождения схемы и кода.
- (-) WSGI — асинхронности нет (для MVP не важно, но сужает путь роста).

## Решение

**Backend API строится на FastAPI** (запуск — `uvicorn`, зависимости — через uv).

Сопутствующие решения:
- Pydantic-модели DTO — единый источник правды контракта; доменные даты сериализуются как `date` (`YYYY-MM-DD`), технические метки — `datetime` в UTC (соответствует ER-модели).
- OpenAPI-спека генерируется FastAPI и используется фронтендом для проверки/генерации клиентских типов (способ — на усмотрение frontend-области; контракт из кода, не файл-первоисточник).
- SQLAlchemy используется в синхронном режиме (сессии через dependency injection FastAPI).

## Последствия

- Контракт API всегда соответствует коду: расхождение фронтенд/бэкенд выявляется на уровне типов.
- Документация API (Swagger UI) доступна без отдельных артефактов.
- Привязка к Pydantic v2 — актуальная мажорная версия фиксируется в backend-спецификации.

## Отклонённые альтернативы

- **Flask** — см. выше (нет нативных Pydantic/OpenAPI).
- **Django REST Framework** — не рассматривался: монолитный фреймворк и собственный ORM избыточны для компактного read-mostly API; стек SQLAlchemy уже выбран проектом.
