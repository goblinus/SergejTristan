# ADR-0004: Стек фронтенда (toolchain MVP)

- Дата: 2026-10-19
- Статус: Принято
- Контекст: область system, MVP «Дивидендный календарь». Оформлен по итогам ревью спецификаций (раунд 1) на основании предложения frontend-области: `design/frontend/2026-10-19_building-and-tools_frontend.md`.

## Контекст и проблема

Для SPA на Vue.js 3 (Composition API) нужен единый toolchain до начала разработки: сборщик, пакетный менеджер, язык, линтинг/форматирование, тесты. Требования контекста:

- типизированная стыковка с API-контрактом бэкенда (Pydantic/OpenAPI, см. ADR-0002) — нужен TypeScript;
- два экрана, ~15 компонентов, один-два разработчика — приоритет простоты и минимума зависимостей;
- тёмная Material-тема реализуется собственными CSS-токенами (см. `design/ui/2026-10-19_visual-style_ui.md`).

## Критерии выбора

1. Стандартность и скорость настройки для Vue 3 + TypeScript (вес — высокий).
2. Минимум зависимостей и шагов установки (вес — высокий).
3. Воспроизводимость окружения (lock-файл, зафиксированные версии) (вес — средний).
4. Достаточность проверок качества кода для MVP без лишнего инструментария (вес — средний).

## Рассмотренные варианты

### Vite + npm + TypeScript + ESLint + Prettier + Vitest (принято)

- (+) Vite — стандарт экосистемы Vue 3: быстрый dev-сервер, production-бандл на Rollup, proxy к бэкенду из коробки (`/api` -> `localhost:8000`).
- (+) npm — без дополнительной установки; `package-lock.json` в репозитории обеспечивает воспроизводимость.
- (+) ESLint 9 (flat config) + `eslint-plugin-vue` + `@typescript-eslint` — стандарт для Vue 3 + TS; Prettier отдельно за стиль (без пересечения обязанностей с линтером).
- (+) Vitest нативно интегрирован с Vite; в MVP тестируются только `utils/` и композаблы.
- (-) Нет — рисков для масштаба MVP не выявлено.

### Отклонённые альтернативы

- **pnpm/yarn** — преимущества (скорость, workspaces) не окупаются без монорепозитория и параллельной разработки.
- **Nuxt/SSR** — избыточен: статический SPA, SEO не требуется (локальное однопользовательское приложение).
- **UI-библиотека (Vuetify и аналоги)** — отклонена документом по темизации frontend: чистый CSS + CSS-переменные из ui-гайда (полный контроль тёмной темы, меньший объём).

## Решение

**Toolchain фронтенда MVP:** Vite 5, npm (Node.js LTS >= 20, версия в `.nvmrc` и `engines`), TypeScript 5 (строгий режим, `vue-tsc --noEmit` обязателен), ESLint 9 (flat config, `vue3-recommended`, `no-restricted-imports` для границ слоёв), Prettier, Vitest (только `utils/` и композаблы), vue-router 4. UI-библиотека не используется — собственные атомы `components/ui/` на CSS-токенах ui-гайда.

Сопутствующие решения:
- Единственные production-зависимости MVP: `vue`, `vue-router`.
- Дата-слой — `Intl.DateTimeFormat` и единый helper `utils/date.ts`; сторонняя date-библиотека не вводится без отдельного согласования.
- Структура каталогов и скрипты — по `design/frontend/2026-10-19_building-and-tools_frontend.md` (детализация решения, настоящий ADR — доминирующий документ).

## Последствия

- Фронтенд поднимается двумя командами (`npm ci`, `npm run dev`); typecheck/lint/test доступны из коробки.
- Границы слоёв (`types` <- `api` <- `composables` <- `components`/`pages`) подкреплены ESLint-правилом, а не договорённостью.
- Критерий пересмотра: появление сложных контролов (data-table, date-picker — пересмотр UI-библиотеки), потребность в SSR/гидрации, рост числа разделяемых серверных ресурсов (пересмотр решения «без Pinia» — остаётся на уровне frontend-спецификации состояния).
